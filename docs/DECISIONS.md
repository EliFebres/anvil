# Decisions

Choices made while hardening anvil for regulated, restricted-network environments, each with the reason. Where two options were reasonable, the more restrictive one was taken. Newest phase last.

## Taken with the repository owner before the run

- **The work continues on `enterprise/hardening` and draft pull request #43.** The branch already held the first round of hardening (removals, repository trust, the file jail, the scrubbed child environment, one HTTP module, the managed policy). Starting again from `main` would have redone that work for no gain.
- **The Ticket schema leaves anvil.** `anvil-types` no longer has `Ticket`, its validator, `ticket::dirs` or the `--schema` binary. The separate repository that consumed the ticket schema still imports them at a pinned commit, so it keeps building; before it moves its pin past this branch it must copy `Ticket` and `ticket::dirs` into its own types crate. Nothing in this repository was changed to accommodate it.
- **This plan overrides the decisions of 2026-11-17 where they conflict.** herdr reporting is deleted rather than kept behind a policy switch. HTTP MCP servers come back only behind the network allowlist of a later phase. Provider tolerance for self-hosted servers and the `anvil doctor` acceptance test stay on the roadmap.

## Phase 1: removals

- **`classify.rs` and `signal.rs` are removed with ticket drafting.** Their only consumer was `anvil ticket draft`: the session end classified records into `signals.jsonl`, and nothing else read that file. `anvil stats` reads the records directly and is unaffected.
- **The `[telemetry]` table is removed.** It only held the thresholds that turned statistics into ticket signals.
- **A configuration that still sets a removed table fails to load.** `[tickets]`, `[telemetry]` and `[integrations]` join `[update]` and `[notify]`: anvil stops and names the table and why it is gone, instead of ignoring it. Silently ignoring it would let someone believe a feature is still on.
- **`anvil memory` is gone, not only `anvil memory learn`.** `learn` was its only subcommand. Facts and standing rules stay and are reached as before (the end-of-session proposals, `rule: <text>`, `anvil rules`).
- **The managed policy's `summarizer_calls` now covers one call.** With the start-of-session rule proposals deleted, it switches only the end-of-session memory summarizer.
- **`anvil setup` writes one example provider named `endpoint`.** It is the same name `anvil setup --endpoint` writes, so running that command replaces the example in place. The example URL is `https://models.internal.example/v1`: the `.example` domain is reserved and never resolves, so an unedited example cannot reach a real host, and it uses https so it passes the egress rules unchanged. Its key variable is `ANVIL_ENDPOINT_KEY`. Under a managed policy, `anvil setup` without `--endpoint` is still refused, because the example would not be on the policy's allowlist.
- **`anvil config init --global` writes the same single example.** The template used to describe a rented GPU behind a vendor's proxy, which is a hosted service; it now describes a server on the organization's own network.
- **Hosted APIs are documented, never written.** The Anthropic and OpenAI protocol adapters stay, and README.md shows one hosted provider entry for a user who adds it by hand.
- **The build commit is read at compile time, without a build script.** `anvil --version` prints `<version> (<commit>)` when the release build sets `ANVIL_BUILD_SHA`, and the version alone for a build from source. A build script would run code at build time for no extra benefit. The release workflow has to set the variable; that change belongs to the supply chain phase.
- **`anvil scan-keys` still reads a repository's `.anvil/.env`.** It never loads it into the environment; it reads the values only to fail when one of them appears in a tracked file. Nothing a repository ships can set an environment variable of anvil.
- **The old-name check has no exceptions.** With the migration module gone, `just no-old-name` and the CI step search the whole tree. The CI step was edited in place, ahead of the supply chain phase, because leaving the exceptions would have pointed at files that no longer exist.
- **An MCP definition may only reference variables a child receives.** `${VAR}` in an MCP server's `command`, `args` and `env` used to read anvil's whole environment, so a trusted repository's `.mcp.json` could copy a provider key loaded from `~/.anvil/.env` into its server. Expansion now draws only from the child environment allowlist plus `[tools] pass_env`. A reference to any other variable is an error that stops that server and names the variable, rather than expanding to empty: an empty value would start the server in a state the user did not intend and hide why. The check runs when the server is started, after `[tools] pass_env` is known, and applies to the user's own `~/.anvil/mcp.toml` as well, because the risk is the same whoever wrote the file. The trust prompt now shows each definition as written, including its environment entries, and never an expanded value.

## Phase 2: managed policy

- **One path per system, and macOS uses `/etc/anvil`.** The plan names `/etc/anvil/policy.toml` for Linux and macOS, so the former `/Library/Application Support/Anvil` path is gone. Windows uses the literal `C:\ProgramData\anvil\policy.toml` rather than `%ProgramData%`: an environment variable is a lower layer the user controls, so reading the path from one would let the user move the policy.
- **Windows ownership is read as SDDL from `Get-Acl`, not from `icacls`.** `icacls` prints principals by localized name, so a German or Japanese Windows would need its own list of group names. `icacls /save` gives security identifiers but writes them to a file, which would have to sit in a folder the user can write while anvil reads it back. `Get-Acl` prints SDDL with security identifiers on stdout. PowerShell is started by its full path under `C:\Windows\System32` with a cleared environment and `-NoProfile`, because the user being constrained controls `PATH`, `PSModulePath` and their profile. Unknown SDDL is a failure, not a pass.
- **Ownership checks treat delete and change-permission as write.** Deleting the policy file would put anvil back into unmanaged mode, and the right to change permissions or ownership leads to write access, so each of these counts as a right only administrators may hold. Administrators, SYSTEM and TrustedInstaller are accepted; `CREATOR OWNER` entries are ignored because they only describe what new child objects get.
- **The ownership check does not run in `anvil policy check` unless `--ownership` is given.** An administrator validates a draft in a working folder before it is installed; requiring root ownership there would make the command useless in a pipeline.
- **The policy is schema version 1 and lists only keys that are enforced now.** CA bundle, client certificate and proxy (Phase 4), HTTP MCP hosts (Phase 4), `[shell]` (Phase 3), redaction and transcript modes (Phase 5) and `[audit]` (Phase 6) are added by those phases. Until then a policy that names them is refused as an unknown key, which is the safe failure. `policies/restricted.toml` gains the shell allowlist and the required audit sink in those phases.
- **The forced profile is replaced by policy `deny` and `ask` lists.** A profile file next to the policy was a second file to own and check; two lists in the policy say the same thing in one place. `--profile` is no longer refused under a policy: a profile is a lower layer like the user's configuration, and anything in it that conflicts with the policy is an error naming the key.
- **`allow_skip_prompts` is split into `allow_yes`, `allow_allow_tool` and `allow_always`.** The plan asks for each switch separately, and an organization may reasonably allow pre-approving one tool while forbidding `--yes`.
- **A user `allow` rule conflicts with a policy rule when it names the same tool and the policy rule has no pattern or the same pattern.** Deciding whether two arbitrary globs overlap is not reliable; this rule catches the cases a person would write by hand and is explained in the error. The policy's rules are added on top of the user's in every case (`Permissions::tighten`), so an allow rule the check does not catch still cannot loosen a policy `deny` or `ask`.
- **A saved `always` rules file is an error when `allow_always = false`.** Reading it would let rules saved before the policy was installed stay in force; ignoring it silently would break the rule that conflicts are never ignored. The error names the file so the user can delete it.
- **Conflicts in anvil's own files are errors; items from files shared with Claude Code or a repository are left out with a note.** (Replaced for `~/.claude` in "Phase 2: review fixes".) `~/.anvil/settings.json`, `~/.anvil/mcp.toml` and `~/.anvil/skills` are anvil's configuration, so a hook, server or skill there that the policy forbids stops anvil with the policy key. `~/.claude/...` files belong to another tool the developer may use alongside anvil, and a repository's files are its content, not the user's configuration; refusing to start because they exist would make anvil unusable next to Claude Code. They are not loaded, and a note names the policy key.
- **MCP allowlist entries name both the server and its program.** A name alone can be reused by any definition, and a program alone can be started with any arguments under a trusted name; requiring both matches the plan's "named servers" without trusting the name by itself.
- **`[features] skills = "bundled"` means the skills shipped next to the source tree.** A release binary carries no bundled skills folder today, so on most machines `bundled` loads nothing; it exists so a policy can say "no third-party skills" without turning skills off for source builds.
- **`[features] memory` covers facts and the end-of-session summarizer, not standing rules.** Rules live in `~/.anvil/rules.toml`, outside `~/.anvil/memory`, are written only when the user types `rule:` or runs `anvil rules`, and never involve a model call. The former `[sessions] summarizer_calls` key is folded into `memory`.
- **`[projects] allow_trust` defaults to `false`.** It is the more restrictive choice. A repository's `deny` and `ask` rules still apply without trust, because they only tighten; the former `[project] config = false`, which also dropped those rules, is gone.
- **`[files] extra_roots` are read-only, and the user's `[tools] extra_dirs` is an error under a policy.** The plan calls them readable roots, and a user folder outside the workspace is exactly what an organization would want to decide centrally.
- **Session token ceilings cap the default silently and refuse an explicit excess.** The built-in default (2,000,000) is not a setting anyone chose, so lowering it to the ceiling is not overriding a lower layer; a value the user wrote is, so it is an error. The same holds for `anvil build` caps.
- **`policy: unmanaged` goes to stderr with the line renderer.** Its stdout stays byte-identical for scripts. The full-screen UI shows the same fact as a `policy` row on its startup screen.
- **The policy hash is the SHA-256 of the file's bytes.** `anvil_types::policy::label` returns `sha256:<hex>` or `unmanaged` for the audit records of Phase 6.
- **The test that shows an environment variable cannot escape the policy works through `home_dir_from`.** `std::env::set_var` is `unsafe` in Rust 2024 and the workspace forbids `unsafe`, so the test passes the value `ANVIL_HOME` would have to the same function `home_dir` uses.

## Phase 7: supply chain and releases

- **`actions/attest` instead of `actions/attest-build-provenance`.** The latter's README says that since v4 it is a wrapper around `actions/attest` and that new workflows should use `actions/attest` directly. Both were at v4.2.2 when checked (2026-11-19).
- **No `artifact-metadata: write` for the release.** The `actions/attest` README lists it, but only for the storage record it creates when `push-to-registry` is set, which anvil does not use. Leaving it out keeps the release to three write scopes: `contents`, `id-token`, `attestations`.
- **Write scopes at the top of `release.yml`, narrowed per job.** The permission test reads the top-level block, so the union of what the release needs is declared there and each build job narrows itself to `contents: read`. The test now also refuses any job-level block that grants more than `read` or `none`, so a job cannot widen the grant unnoticed.
- **`cargo deny` is installed with `cargo install --locked` in CI, not through `EmbarkStudios/cargo-deny-action`.** The action runs a Docker image that downloads the cargo-deny binary without a checksum and uses an older Rust image than `rust-toolchain.toml`. Building the pinned version (0.22.0) from crates.io with its own lockfile keeps one less third-party component in CI, at the cost of about two minutes per run.
- **chrono's unmaintained advisory is ignored with a reason.** RUSTSEC-2026-0543 marks `chrono` unmaintained with no safe upgrade. It reports no vulnerability. Replacing chrono with `jiff` or `time` touches every crate and is a roadmap item, not part of this phase.
- **The workspace crates are `publish = false`.** anvil ships binaries only. Without it, cargo-deny treats the path dependencies between workspace crates as wildcard versions of publishable crates and fails the `wildcards = "deny"` rule.
- **One SBOM for the anvil binary, all targets.** `cargo cyclonedx --target all` lists the dependencies of every platform in one CycloneDX 1.5 file, which is simpler for a reviewer than one file per target and never omits a platform-specific crate.
- **No build cache in the release workflow.** `Swatinem/rust-cache` was removed from `release.yml` so a release is built from a clean state; CI keeps the cache.
- **Release notes come from `CHANGELOG.md`.** The release job fails when the tagged version has no section, so a tag cannot publish without a changelog entry.
- **`aarch64-apple-darwin` added, `x86_64-apple-darwin` not.** The `macos-14` runner is Apple silicon and builds natively; an Intel build would need cross-compilation or a deprecated runner.

## Phase 2: project trust

- **Loosening keys in a repository's `.anvil/config.toml` are errors, not warnings.** The plan says such a file "may not" change providers, roles, the shell program or allow rules. An error that names the key is more restrictive than ignoring it, and it tells the developer the repository is trying something, instead of letting them believe a setting is active. The error covers `[providers]`, `[roles]`, `[tools]` (shell, check, `pass_env`, `extra_dirs`), `[network]`, and `allow`, `default` and `allow_tools` under `[permissions]`. Other unknown keys are still ignored with a warning, as decided on 2026-11-17, because they change nothing.
- **A repository's `allow` rules live only in `.anvil/permissions.toml`, and wait for trust.** `default` and `allow_tools` stay errors there: a default would allow everything unnamed, and pre-approval would skip prompts for a whole tool.
- **A trusted repository's `allow` is the weakest rule.** It decides only a call that no `deny`, `ask` or `allow` of the user's or the repository's matches and that the user's own `default` does not cover. It replaces the tool's built-in default and nothing else, and it never lifts the blocked-command list or `shell_programs`. This keeps the user's explicit choices above anything the repository says.
- **What the trust digest covers.** `.anvil/permissions.toml`, `.anvil/settings.json` and `.local`, `.claude/settings.json` and `.local`, `.mcp.json`, `ANVIL.md`, `CLAUDE.md`, `CLAUDE.local.md`, `.claude/CLAUDE.md`, every `CLAUDE.md` in a subfolder (found honoring `.gitignore`), the instruction text as anvil loads it (so a changed `@import` target counts), and every file under `.claude/skills`, `.claude/commands`, `.claude/agents`, `.anvil/skills`, `.anvil/commands` and `.anvil/agents` (skill scripts included). Each file enters with its relative path, so adding, removing or renaming one changes the digest. `.anvil/config.toml` is left out: it can only tighten.
- **A refusal is not pinned.** "Do not trust" stays whatever the repository changes, because it loosens nothing; only a decision to trust is tied to content.
- **Trust recorded before digests existed no longer counts.** The old `trust.toml` format still loads, but a bare `trusted` entry is treated as undecided, so the user is asked once more. A bare `untrusted` entry still counts.
- **Writes to files that grant power are refused, not asked about.** Before this phase a write to a hook settings file asked a person. The plan says tools may never write these files, so the prompt path is gone: `.anvil/config.toml`, `.anvil/permissions.toml`, any `settings*.json` in a `.claude` or `.anvil` folder, `.mcp.json`, and everything under `~/.anvil` are refused by `ToolContext::checked_path` before any rule is consulted. The match ignores letter case on every system, which on Linux also refuses names anvil would not read; that costs nothing and avoids a case-folding mistake on Windows and macOS.
- **One path decides trust, with the policy switch as a parameter.** `trust::decide` and `trust::run` take `allow_trust`, and the CLI always passes `anvil_types::policy::allows_project_trust(policy)` (`true` in unmanaged mode). When it is `false`, nothing is asked or recorded, a stored trust is ignored, and `anvil trust` (without `--revoke`) is an error.

## Phase 2: review fixes

- **Only a missing policy is unmanaged.** `load_checked` used `Path::exists`, which is `false` for any error, so a policy folder the user may not list ran anvil unmanaged. The file's `symlink_metadata` must now say not found, and its folder must be not found or a folder; any other error (permission denied, a folder that is a file) stops anvil with the reason. A policy folder that exists while the file does not is still unmanaged, because an empty `/etc/anvil` is an ordinary state and the file lookup inside a folder the user may not list already fails with permission denied.
- **`default = "allow"` counts as `--yes`.** It approves every call no rule names without a person, so under `allow_yes = false` it is an error naming that key wherever a user layer sets it: the configuration, a profile, or the saved rules file under `~/.anvil/permissions/`. A repository's files could already not set `default`. No other route approves an unnamed call: rules name one tool, and there is no wildcard tool.
- **Forbidden items in `~/.claude` are errors, like `~/.anvil`.** The plan says a conflict is never ignored silently, and both folders are the user's own configuration. The cost: a developer with Claude Code hooks, MCP servers or skills in `~/.claude` that the policy forbids cannot start anvil until they remove them or the administrator allows them. The error names the policy key and the file.
- **Forbidden items a trusted repository ships stay a visible note.** An error would make every trusted repository with a `.mcp.json`, hooks or skills unusable under a policy that turns those off, and the developer cannot fix it without editing the repository. The note on stderr names the policy key and the file, so it is not silent; the item never loads.
- **A repository that links a skill, command or agent is never trusted.** The digest skipped symbolic links while the loaders followed them, so a link's target could change after trust. Following links in the digest was the other choice; refusing is more restrictive and simpler: it needs no change to the loaders, and the digest never walks a link that points at a large folder outside the repository, which matters because the digest is computed before trust. Any symbolic link or Windows junction inside `.claude` or `.anvil` `skills`, `commands` and `agents`, or in place of those folders or of `.claude` and `.anvil` themselves, makes `decide` return untrusted with a note and `anvil trust` an error. A repository that wants to share skills between tools replaces the link with a copy.
- **Write paths Windows would fold are refused, not folded, on every system.** Windows strips trailing dots and spaces from each name and reads `name:stream` as a data stream, so `.anvil/config.toml.` passed the protected-file check as written and created `.anvil/config.toml`. `ToolContext::checked_path` now refuses a write path whose `win32_fold` differs from what the model wrote: a name ending in a dot or space, a name of only dots, or any `:` after the drive prefix. Refusing is simpler than writing the folded name and more restrictive; it means the path checked is always the path written. It runs on Linux and macOS too, where such names are legal, so the behaviour and the tests are the same on every system; the cost is that a file tool cannot create `notes.` or `a:b.txt` there, which a shell command still can. (Phase 3 review fixes extend this to reads and searches.)
- **Files that hooks and MCP servers run are protected and pinned.** A trusted hook such as `sh scripts/fmt.sh` runs without a prompt, so a model that could rewrite `scripts/fmt.sh` with `write_file` had unprompted code execution. Every word of a loaded hook command, and an MCP server's program and arguments (plus the value of a `--key=value` word), that resolves relative to the project root to an existing file inside it is now refused to the file tools (`Workspace::protected_files`) and added to the trust digest, so a change made any other way asks again next session. Words are split at white space, quotes and shell operators, which errs towards protecting too much; a file created after the session started is not covered until the next session, and a script outside the repository is outside the file tools' reach already. The user's own hooks in `~/.anvil` and `~/.claude` protect the project files they name too, because they run the same way.
- **`anvil policy show` lists every key, sorted, and the user section lists every key the policy constrains.** Optional policy keys (`transcript_dir`, `retention_days`, `session_tokens`, `build_tokens`, `build_usd`) used to vanish when unset; they now print as `(default: <meaning>)`. A test compares the keys printed for a minimal policy with those of a policy that sets every optional key, so a new optional key cannot be left out. The user section gains the optional roles, `allow_http_hosts`, `extra_dirs`, every `[permissions]` key the checks read and `always_summarize`, under a heading so its `[permissions]` lines are not read as the policy's. The output is a snapshot test.
- **Hard links and approved shell commands are documented, not blocked, in this phase.** Both need a shell command a person approved (or `--yes`), which runs with the user's rights; SECURITY.md says so under "What is not enforced". Detecting a hard link would need the link count on every write and still would not stop the shell command itself. Controls on what a shell command may touch belong to the shell modes of Phase 3 and are described only once they exist.

## Phase 3: tool confinement

- **`[tools] pass_env` keeps its name.** The plan calls it `env_pass`; the key already existed as `pass_env` in configurations and documents, and renaming it would break them for no gain in safety. A name listed there is passed even when it is a provider's `api_key_env` or looks like a secret, as the plan says ("never passed unless listed by name").
- **A policy without `[shell]` turns the shell off.** Every other policy key defaults to the restrictive choice, and `off` is the most restrictive mode. Both shipped policies set `[shell]` explicitly (`restricted.toml`: `allowlist`; `standard.toml`: `ask`). Two Phase 2 tests that call `shell` under a minimal policy now add `[shell] mode = "ask"`. Without a policy the default stays `ask`.
- **`shell_programs` is folded into allowlist mode.** One matching mechanism remains: each `shell_programs` list becomes one allowlist layer of `<program> *` patterns, and a command must match a pattern in every layer (the user's, the repository's, the policy's). Commands under `shell_programs` therefore now start without a shell too. The key stays, because it is the one way a repository can narrow the shell; `profiles/strict.toml` moved to `[shell] mode = "allowlist"`.
- **Layers intersect.** A user allowlist under a policy allowlist is a second layer, so the user can only narrow what the policy allows. Of two modes, the stricter applies; a looser user mode is an error naming `[shell] mode`.
- **The parser refuses more than the list in the plan.** Besides `;`, `&`, `|`, `<`, `>`, backticks, `$(`, braces and line breaks, it refuses parentheses (PowerShell and cmd grouping) and NUL. Quotes group words and are removed, with no escapes inside them; a backslash is an ordinary character so Windows paths work. A bare `$` is allowed, because no shell is there to expand it.
- **A deny category is lifted only by a rule that names the command.** "Unless a rule allows them by name" is read as: an `allow` rule whose pattern text contains the matched phrase (`shell:curl *` names `curl`; `shell:git push origin *` names `git push`), or, under an allowlist, a matching pattern in every layer that names it. A bare `shell` rule or `shell:*` no longer lifts the four destructive patterns, which is stricter than before; `default = "allow"` never did.
- **The categories hold more than the plan's list.** `ncat`, `netcat`, `Start-BitsTransfer` and `bitsadmin` are network clients, `doas` is a privilege tool, and `gem install`, `npm i`, `npm add` and `npm ci` count as package installs. Every word of a command is checked, not only the program position, so `cargo test -- ssh` is refused too; a naming rule lifts such a false positive.
- **The container keeps a writable `/tmp` in memory.** A read-only root file system leaves most toolchains without a temp folder, so `--tmpfs /tmp` is added; it holds no host data, so the workspace is still the only host folder mounted. The workspace is mounted read-write so commands can build. No host variable enters the container, only `HOME=/tmp` and `PYTHONDONTWRITEBYTECODE=1`. Defaults: user `65534:65534` (root is refused), 2 GB of memory, 256 processes. Each run is named, and a run that times out is killed by name, because killing the docker client does not stop the container.
- **The container executor covers the `shell` tool, checks and acceptance commands, not hooks or MCP servers.** Those are separate policy features (`[features] hooks` and `mcp`), off by default; running them in containers is on the roadmap.
- **Under a policy the executor and the container come only from the policy.** A user `[shell] executor` that differs, or any user `[shell.container]`, is an error, even where it would be stricter: the policy names the image an organization has vetted.
- **A `[tools] check` command must fit the policy's shell mode.** It is an error under `off`, and under `allowlist` when no policy pattern allows it, because the check runs through the same runner as the shell tool.
- **`anvil build` follows the shell.** It refuses to start while the shell is off (an item is done only when its acceptance command ran), and the acceptance command and a detected check now go through the same permission path as the model's `shell` calls, prompting unless `--yes` was given. Before, they ran without any check.
- **A repository may not set `[shell]`.** Some values would only tighten, but the shell mode belongs to the user and the administrator; an error naming the key is clearer than accepting some values and refusing others.
- **anvil's git calls start from a cleared environment.** They get the child list plus the author and committer identity and the variables that locate the user's own git config (`XDG_CONFIG_HOME`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`), so commits keep the user's identity. `SSH_AUTH_SOCK` and credential variables are not passed: these calls never contact a remote.
- **The secret list errs on the side of refusing.** `credentials*` matches any file whose name starts that way, and a repository's `.git/config` is refused for reading (it can hold a remote URL with a token); the rest of `.git` stays readable. `list_dir` now leaves refused entries out, as `glob` and `grep` already did.
- **The real container test is ignored by default.** It is `#[cfg(target_os = "linux")]` and `#[ignore]`, returns early unless `ANVIL_CONTAINER_TEST=1`, and a step on the ubuntu CI job runs it with `--ignored`. It uses `alpine:3.20` by tag (or `ANVIL_CONTAINER_IMAGE`); pinning it by digest is left to the supply chain work.

## Phase 3: review fixes

- **Folded names are refused for reads and searches too.** A read of `server.pem.` passed the `*.pem` check as written and Windows opened `server.pem`; `jx./out.txt` went through a junction the check never saw. `checked_path` now refuses every path whose `win32_fold` differs from what the model wrote, for every file tool and on every system. Opening the resolved path instead was the other choice; refusing is more restrictive and keeps one rule for reads and writes.
- **Hard links stay documented, not detected.** Std exposes the link count only through platform extensions (`MetadataExt::nlink` on Unix; nothing stable on Windows), so a portable check is not trivial. SECURITY.md now says reads through a hard link are not detected either.
- **Every non-test `Command` clears its environment, with no exception.** `anvil doctor` (`git --version`, `sh -c "echo ok"`) and `anvil setup` (`icacls`) passed the full environment. Both now clear it, and `Shell::command` clears it itself so a future caller cannot leave it out. Doctor's git probe goes through a new `anvil_core::git::standalone`, which applies the same safe settings and runs in the temp folder, rather than an exception in `one_git_entry.rs`. `children_start_clean.rs` scans the source: `Command::new(` must be followed by `env_clear()` within twelve lines; its exception list is empty.
- **Allowlisted git refuses every option before the subcommand but seven.** `-c`, `--config-env`, `-C`, `--git-dir`, `--work-tree`, `--exec-path`, `--namespace`, `--super-prefix` and `--attr-source` are the ones the review named; refusing all but `--no-pager`, `-P`, `--no-optional-locks`, `--literal-pathspecs`, `--no-replace-objects`, `--version` and `--help` is more restrictive and needs no list of new options as git adds them.
- **`-o` and `-O` are refused for every git subcommand.** `-o` writes a file for `format-patch` and `archive` but means `--others` for `ls-files` and `--only` for `commit`; refusing it everywhere is simpler and the long forms still work. `-O` is a pager for `grep` and an order file for `diff`; both go. Long options are refused by name and by any abbreviation of three letters or more, since git accepts abbreviations; `--text` is the one real option that is also such an abbreviation and stays allowed.
- **Aliases never run under an allowlist.** A subcommand that names an alias from any config file (the user's too) is refused, and so is a repository whose own config defines any alias, `!` or not, because a model allowed `git config` could plant one. The user's own `diff.external`, filters and signing program still run: they are the user's choice, as for anvil's own git calls. External diff and text conversion are also turned off on the command line for diff subcommands and `blame`.
- **The repository-config refusal for allowlisted git covers more keys than anvil's own git calls.** Besides filters and signing programs it refuses aliases, `diff.external`, diff driver `textconv` and `command`, merge drivers, diff and merge tools, credential helpers, `core.askPass`, `core.sshCommand`, `core.gitProxy`, `core.alternateRefsCommand`, `core.worktree` (which would move git's writes outside the project), `interactive.diffFilter` and submodule `update` commands. anvil's own calls run fixed commands that use none of them, so they keep the shorter list and do not refuse repositories with local aliases.
- **Path arguments are checked for every allowlisted program, on the arguments and on `=` values and attached short-option values.** A word that starts with `~` is refused outright, since a program may expand it; a rooted, drive, UNC or `..` word must resolve inside the project root (not an extra folder or the session folder). On Windows a word such as `/i` is rooted and resolves outside, so Windows-style switches are refused; the programs an allowlist names take `-` options. In the container a word such as `/workspace/x` is refused too, since the check runs against the host path.
- **Shipped allowlists are narrowed.** `profiles/strict.toml` drops `cargo *` (`cargo publish`, `--config` naming a program), `git *` (`git config` plants aliases and programs), `just *` (any recipe) and `rustc *` (`-C linker=<program>`) for named subcommands, and keeps `just check` as the project's own check. `policies/restricted.toml` keeps its list, with the residual risk of each pattern in a comment. `cargo build`, `check`, `test` and `clippy` still run build scripts and tests the model wrote; that is their purpose, and the container executor is the boundary for it.
- **One existing test changed on purpose.** `allowlist_mode_starts_the_program_without_a_shell` proved that no shell expands `$HOME` with `git -c anvil.probe=$HOME config --get anvil.probe`, which is now refused; it uses `git rev-parse --sq-quote $HOME` instead. `the_shipped_strict_profile_loads_as_a_profile` now asserts the narrow patterns instead of `cargo *`.
- **The container user is parsed, and root is refused in any spelling, for the group too.** `user` must be `uid` or `uid:gid`, each all digits or a name that starts with a letter or `_` (so `+0`, `-1` and an empty part are refused); a part that is all zeros or `root` (any case) is refused. Names other than `root` are accepted, although an image could map one to uid 0; the policy names the image, so that stays the administrator's choice.
- **The workspace's `.git` is mounted read-only in the container.** A second bind mount of `<workspace>/.git` at `/workspace/.git` with `readonly` covers the read-write workspace mount, so a container command cannot plant `.git/hooks/*` or change `.git/config` for the user's next git on the host. A git command in the container that writes (`git add`, `git commit`) now fails; that is the cost. The rest of the workspace stays writable by design, and SECURITY.md says what that leaves.
- **The source scans read past `#[cfg(test)] mod name;`.** `children_start_clean.rs` and `one_git_entry.rs` used to stop at the first `#[cfg(test)]`, which in `tools/mod.rs` is a module declaration near the top, so most of that file went unchecked. Both now stop only at an inline test module (`#[cfg(test)]` followed by `mod name {`).

## Phase 4: network egress

- **The check runs in the client's send path.** `http_client` returns an `HttpClient` that never hands out the reqwest client, and `HttpRequest::send` checks the final URL before `execute`, so no caller can skip it. Redirects stay off, so one check per request covers every host the request reaches. The check at provider build stays too, so a refused endpoint fails before its key is read.
- **The unmanaged allowed set is what the user's files name.** It holds the `host:port` of every provider `base_url` and every HTTP MCP `url` in `~/.anvil/mcp.toml`, plus those of a repository's `.mcp.json` and `.claude/settings*.json` once the user trusts it; an untrusted repository adds nothing. `anvil setup --endpoint <url>` probes under a set holding the URL the user typed.
- **Every configured endpoint is checked at startup, and a refusal is an error.** `Wiring::check_endpoints` covers providers and HTTP MCP servers, including a trusted repository's, in unmanaged mode. Under a policy, an HTTP server a repository ships whose host is not allowed is left out with a note naming `[network] allowed_hosts`, like other forbidden repository items; the user's own is an error. `anvil doctor` skips the startup check so it can report a refused endpoint as a row instead of stopping.
- **`allow_http_hosts` stays user-only and an error under a policy.** The policy's `require_tls` alone decides plain http there.
- **The CA bundle replaces the system store.** `ca_bundle` uses reqwest's `tls_certs_only`, not `tls_certs_merge`, so only the administrator's authorities are trusted. An administrator who needs a public endpoint adds its roots to the bundle.
- **TLS file paths must be absolute, and the certificate and key come together.** A relative path would depend on the directory anvil starts in. The files are read when the client is built, so an unreadable or invalid one stops the provider with the key name.
- **Proxy mode `none` ignores the environment, and a proxy URL may not carry credentials.** `none` calls `no_proxy`, which also turns off reqwest's system proxy lookup. The policy file is readable by every user, so `user:password@` in it is refused. The proxy itself is not checked against `allowed_hosts`: the policy names it, and `anvil doctor --egress` lists it as a destination. A plain `http://` proxy is accepted, because requests to https endpoints are tunneled through it with TLS end to end.
- **Proxy and TLS keys exist only in the policy.** Without a policy anvil uses no proxy and the system store. This drops the old behaviour of honoring `HTTPS_PROXY` in unmanaged mode, which the brief chose as the more restrictive default; a user-level setting is on the roadmap.
- **A secret header is bound to its configured host.** `HttpRequest::api_key` takes the URL the key belongs to and adds the header only after the egress check, only when the request's `host:port` equals that URL's. Providers bind their key to `base_url`, the model probe to the probed base, and HTTP MCP servers bind every header their definition sets to their `url`. The header value is marked sensitive and redacted from `Debug`.
- **HTTP MCP is minimal and allowlisted.** It is the streamable HTTP transport of protocol 2025-06-18 (the revision the stdio client already speaks): one POST per message with `Accept: application/json, text/event-stream`, `MCP-Protocol-Version` on every request, the `Mcp-Session-Id` the server assigns, and either a JSON or an SSE answer, read up to 8 MiB. The optional GET stream is not opened, a request the server sends inside a stream is answered with "method not found", and the older SSE transport is refused. An expired session (404) is reported, not renewed; that and protocol 2026-07-28 are on the roadmap.
- **An HTTP MCP rule names the exact URL.** `mcp_servers` entries take `url` instead of `command` (exactly one), matched apart from a trailing `/`; a host match alone would allow every path on a shared gateway. Its `host:port` must also be in `allowed_hosts`, under `mcp = "on"` too.
- **HTTP MCP headers follow the variable rule of local servers.** A header may use `${VAR}` only for a variable that programs anvil starts may receive (`child_env` plus `pass_env`), so a definition cannot copy a provider key into a header sent to another server. The trust prompt lists an HTTP server's URL and header names, never header values.
- **The guard test covers more than the brief's two spellings.** `one_http_client.rs` forbids `Client::new(`, `Client::builder(`, `Client::default(`, `ClientBuilder::new`, `reqwest::get(`, `reqwest::blocking` and switching the lint off, in test code too, and a second test fails if a crate other than `anvil-core` depends on reqwest.
- **TLS and proxy tests use real connections.** A rustls server on loopback with committed test-only certificates (`anvil-core/tests/fixtures/tls`, EC P-256, 100 years) proves the CA bundle and mutual TLS; `tokio-rustls` is a new dev-dependency already in the lock through reqwest. The proxy-variable test runs the test binary again as a child with `HTTP_PROXY` set, because changing this process's environment needs `unsafe`; like every other child, it starts from a cleared environment refilled from `child_env::vars()`, plus the proxy and test variables.
- **FIPS is written down, not attempted.** See `docs/ROADMAP.md`.

## Phase 4: review fixes

- **The client guard names types, not the `Default` methods.** The review built a client with `reqwest::ClientBuilder::default()` and `<reqwest::Client as Default>::default()` past both the test and clippy. Clippy's `disallowed-methods` cannot list `reqwest::Client::default` or `reqwest::ClientBuilder::default`: it does not resolve paths to trait implementations and rejects both as unreachable. `disallowed-types` for `reqwest::Client` and `reqwest::ClientBuilder` catches every spelling, `Default::default()` included, so it was added instead, and `net.rs` allows the two types where it builds and holds the client. The text test also refuses the `Default` spellings and every way to silence the lint without naming it (`clippy::all`, `clippy::style`, `allow(warnings)`, `expect(warnings)`, `disallowed_types`), in test code too, and a manifest test refuses those lints at `allow` or `expect` in any `[lints.clippy]` table and in `.cargo/config`.
- **Other HTTP clients are banned twice.** `deny.toml` bans ureq, isahc, attohttpc, surf, curl and curl-sys outright, and allows hyper and hyper-util only as a dependency of reqwest, hyper-rustls, hyper-util and wiremock (a test server). `no_workspace_crate_depends_on_another_http_client` parses every workspace manifest (normal, dev, build and per-target tables, `package =` renames, `[workspace.dependencies]`), so a direct dependency fails `cargo test` before `cargo deny` runs.
- **No non-test code outside `net.rs` names a socket type.** `TcpStream`, `UdpSocket`, `TcpSocket` and `UnixStream` are refused by text in non-test source, the same way `children_start_clean.rs` scans for `Command`. Listeners are not refused; tests are not scanned, because the TLS and proxy tests run servers on loopback.
- **The container engine never pulls.** `container_args` passes `--pull=never`, so a missing image is an error instead of a request to a registry that no anvil rule or `anvil doctor --egress` row covers. Administrators pre-load the image; the CI step that runs the real container test pulls `alpine:3.20` first.
- **Plain http is checked when the configuration loads, in the CLI loader.** `anvil_types::config::validate` cannot do it: it does not know the policy, and under `require_tls = false` a plain-http provider on the network is allowed without `allow_http_hosts` (which a policy forbids the user to set). `check_plain_http` in `crates/anvil-cli/src/main.rs` runs right after the configuration and the policy check load, for every command that reads them, and applies the same `Egress` rule the requests use. It covers provider `base_url`s; HTTP MCP URLs are still checked when a session starts and on every request. The cost: `anvil doctor` now stops at a plain-http provider the rules refuse instead of reporting it as a row; refused hosts that are not a plain-http matter are still rows.
- **The FIPS notes now name the module that would be built.** aws-lc-rs 1.19.0 requires `aws-lc-fips-sys ^0.14.2`; 0.14.4 vendors AWS-LC 4.2.0 although its README still says 3.0.x, so `docs/ROADMAP.md` gives the source's version and leaves the certificate question open.

## Phase 5: data protection

- **Redaction lives in `anvil-types` and is applied in `anvil-core`.** The secret shapes and the `Redactor` are a pure regex module in `anvil_types::redact`, so core, compat and the CLI share them without breaking the dependency rules; `regex` was already a workspace dependency. The scan-keys patterns moved there, keeping their labels, and gained AWS access key ids and JWTs. `anvil_core::guard::DataGuard` applies redaction in `ToolRegistry::execute`, before truncation, the `tool-output/` file and the PostToolUse hook, so the provider, the transcript and the full-output file hold the same redacted text.
- **Private key blocks are redacted but not scanned for.** This repository commits test-only TLS keys on purpose, and other repositories do the same for fixtures; the file tools already refuse `*.key` and `*.pem`. A block cut off by truncation is redacted to the end of the text.
- **Environment values count when the name looks secret or a provider names it.** The names `child_env::looks_secret` matches, plus every `api_key_env`, with values of 8 characters or more that are not placeholders. Shorter values would replace ordinary text. The kind is `env:<NAME>`: the name is not the secret, and it tells the model which variable to ask about.
- **User text is redacted too.** The task, every user message of the loop and of chat, check output fed back to the model and the reviewer's brief go through the same redactor before they are sent or stored, which is the more restrictive reading of "tool results and file reads". The model's own messages and tool arguments are not redacted: they can only repeat what it received, and changing them would corrupt the edits it asks for.
- **Only the policy can turn redaction off.** `[data] redaction` defaults to `true`, also unmanaged; there is no user key. When a policy sets `false`, anvil prints a note on stderr and logs a warning at every session.
- **Counts are logged and recorded, values never.** Each redaction logs its source, total and kinds, and the session log gets a `redacted` record with the same (chat too, since "Phase 5: review fixes"). No event or usage record was added; the log and the transcript are where an administrator looks.
- **Delimiters carry a per-session random nonce, and the prompt does not name it.** `<untrusted-data id="NONCE" source="...">` ... `</untrusted-data id="NONCE">`, with the nonce from a fresh ULID per wiring (shared by subagents). Any `<untrusted-data` or `</untrusted-data` inside the content, in any case and with spaces, has its `<` replaced by `&lt;`, so content can neither close the element nor open a fake one. The base prompt describes the shape without the nonce, so prompt snapshots stay stable; agent tests use the fixed nonce `testnonce`. Anvil's own refusals (denied, unknown tool, invalid arguments, the Plan-state refusal) are not wrapped, because they are instructions from anvil. A PostToolUse hook still sees the unwrapped, redacted output, so existing hook scripts keep working.
- **`[data] transcript` defaults to `off` under a policy.** Every other policy key that keeps data defaults to the restrictive choice, and `off` keeps least; `policies/restricted.toml` uses `metadata` and `policies/standard.toml` `full`. Unmanaged the mode is `full`.
- **What `metadata` keeps.** The meta record (id, time, project path, mode) with the task replaced by its size and SHA-256; states, the baseline tree, the final status; one `turn` record per completion (state, role, token counts, latency, retries); `redacted` records; and for each message its role, byte size and SHA-256, for an assistant turn each tool call's id, name, argument size and argument digest, and for tool results each result's call id, size, digest and error flag. No message text, file contents, command output or tool arguments. Below `full` no `tool-output/` file and no compaction summary file is written. `plan.md` and `summary.md` are still written: the plan is what a person approves and the summary is printed at the end; they go with the folder under `retention_days` and `anvil purge`.
- **Resume refuses below `full`.** `anvil resume` stops with the reason under a policy whose mode is not `full`, and `load_session` refuses a log recorded in `metadata` mode even after the policy changes. `anvil sessions` still lists such sessions. The end-of-session memory step is skipped with a note, since it reads the transcript.
- **`anvil purge --older-than <days>` reuses the retention code.** It removes only folders named like a session id, by modification time, under the policy's `transcript_dir` when one is set. `0` removes every session folder. It is allowed under any policy, since it only deletes.
- **One approvals file for every MCP server.** `~/.anvil/mcp-approvals.toml` keeps, per scope (the repository's canonical path for a server its files define, `user` for the user's own) and server name, the SHA-256 over the canonical JSON (object keys sorted) of the tools sorted by name, each `{name, description, input_schema}`. Keeping project servers in the trust record was the other choice; one file is simpler, and the trust digest already pins the definition itself.
- **The first listing is recorded without a prompt.** The server's identity is already approved (the user's own file, a trusted repository, or the policy's `[features] mcp`), and loading happens before any prompt can be shown in every front end. A later listing that differs stops the server with an error that names `anvil mcp approve <name>`, in managed and unmanaged mode alike; there is no in-session prompt to accept it. Under a policy, `anvil mcp approve` works only for a server the policy allows, because the policy filters the server set first. Superseded in "Phase 5: review fixes": under a policy `anvil mcp approve` is refused and only a `listing_sha256` pin accepts a changed listing.
- **The MCP cache moved under `~/.anvil` and is tied to the approval.** `<project>/.anvil/mcp-cache/`, keyed by a `DefaultHasher` of the definition, let a repository ship a listing whose descriptions reached the prompt without anvil connecting. The cache is now `~/.anvil/mcp-cache/<repository>/<server>.json`, keyed by a SHA-256 of the definition, and is used only when its tools hash to what it records and that is the approved listing. Dropping the cache was the other choice; keeping it under the home costs nothing in safety and keeps startup fast. Old `.anvil/mcp-cache/` folders are ignored. Superseded in "Phase 5: review fixes": the cache is gone and every start lists live.
- **HTTP MCP error bodies lose every sent header value.** Each header value, and each word of one with 4 or more characters (the token of `Bearer <token>`), becomes `[REDACTED:header]`, then the built-in shapes are redacted, before the body is cut to 500 characters. Over-redacting the word `Bearer` costs nothing.
- **Owner-only on Unix through one helper; Windows is checked, not changed.** `anvil_types::private_fs` creates folders 0700 and files 0600 and narrows an existing file when it rewrites it. It covers the data anvil stores (sessions, logs, usage records, status, build state, memory, rules, trust, approvals, the cache, saved rules, configuration and `.env` written by setup and `config init`). Templates, global skill installs and the session's git index were not covered, and existing folders were not narrowed, until "Phase 5: review fixes". Files the file tools write into the project and project scaffolds keep the user's umask, because they are the user's project. On Windows a new file inherits its folder's access list; changing access lists from anvil would need either `unsafe` Win32 calls or another `icacls` child, so `anvil doctor` instead reads the SDDL of `~/.anvil` and `.anvil` with the policy ownership helper and fails a row when anyone but the owner, SYSTEM or Administrators has any access, read included, printing the `icacls` command that fixes it.
- **The log file is created before the appender opens it.** `tracing_appender` opens its file with default permissions, so `logging::init` creates `anvil.jsonl` through `private_fs` first.
- **`[features] memory` needed no code change.** Facts are read only by `memory::prompt_sections`, whose three callers pass `memory_allowed()`, and written only by `finish_session`, which returns before building a provider when memory is off. A test now drives both under a policy and finds `~/.anvil/memory` unchanged.

## Phase 6: audit log

- **Worked in the `D:\Coding\anvil-phase6` worktree.** The brief named the main checkout, but `enterprise/phase6` was already checked out in that worktree, and git does not check one branch out twice.
- **The usage-record crate is renamed, not split.** It is now `anvil-audit` and keeps the usage records next to the new `audit` module, so the dependency rules of the old crate carry over unchanged. Records moved from their old folders under `.anvil/` and `~/.anvil/` to `.anvil/usage/` and `~/.anvil/usage/`; old files are not migrated and `anvil stats` no longer reads them. The removed-table check in `config.rs` and its test keep the old table's name, because a configuration that still sets it must keep failing to load; the DECISIONS lines of Phase 1 name it too.
- **One audit file per session, in the session folder.** `<session folder>/audit.jsonl`, written whatever `[data] transcript` says, and the mirror at `<mirror_dir>/<session id>.audit.jsonl`. A resumed session continues its chain after verifying the file; under `required` a file that does not verify stops it.
- **Canonical form: the record's own JSON, hash last.** The hash is the SHA-256 of the compact serde_json serialization of the record with fields in declared order and without `hash`; the stored line inserts `,"hash":"<hex>"` before the closing brace. Verifying cuts the line at the last `,"hash":"`; since the Phase 6 review fixes it also re-serializes the parsed record and requires the same bytes (see below). No field holds a float.
- **The first `prev` is 64 zeros, not a hash of the session id.** Every record already carries the session id inside its hash, and `verify` refuses a record of another session, so binding the genesis to the id adds nothing.
- **A blank line, or a last line without a newline, is a break.** Both are things anvil never writes; accepting them would let a hand edit pass.
- **Under a policy the log is required by default.** Every other policy key defaults to the restrictive choice, so `[audit] required` defaults to `true` when a policy file exists; unmanaged sessions write the log but are not required, as the run's guidance says. `policies/standard.toml` sets `required = false` explicitly, `restricted.toml` sets `true`.
- **Fail closed means nothing runs after a failed write, not only that the loop is asked to stop.** The loop's future can run several steps without yielding, so a `select!` alone could let a tool call through. A required log therefore sets a `CallGate` that every provider (`Wiring::provider`) and every registry (`Wiring::registry_without_delegate`, subagents included) checks first: a model request fails with `request refused`, a tool call is refused, and the loop runs neither its check command nor the rule checks. `drive` and the chat turn also stop on the failure, and the command ends with an error and a non-zero exit, after the terminal is restored and before memory or Stop hooks run.
- **Records are written synchronously through an event tap.** `EventSink` gained an `EventTap` that sees each event on the emitting thread. Writing from the asynchronous tee would let a permission decision, which the registry reports synchronously, land before the tool call it decided.
- **Permission decisions carry their exact source from the one check.** `Permissions::ruling` returns the decision with the author of the strictest matching rule (`Policy`, `Project`, `User`, `Builtin`); `shell_refusal_by` names the allowlist layer that refused, and a command refused by the allowlist mode as a whole is attributed to the strictest layer's author. A prompt reports who answered through `PermissionPrompt::answer_source` (`StaticPrompt(Yes)` is `--yes`, `StaticPrompt(No)` is `unattended`), and every wrapper forwards it. The policy's shell layer is recognized by its fixed label `POLICY_LAYER`.
- **Policy refusals recorded:** a call the policy's `[permissions] deny` refuses (`permissions.deny`), a command the policy's allowlist refuses (`shell.allow`), and at session start the hooks, MCP servers and skills `Wiring::with_policy` kept from loading (`features.hooks`, the MCP key it printed, `features.skills`). Other policy errors stop anvil before a session exists and are not in any audit log.
- **The user and host come from the environment.** `USERNAME`/`USER`/`LOGNAME` and `COMPUTERNAME`/`HOSTNAME`, then `/etc/hostname`, then `unknown`. This needs no new dependency and no `unsafe`; the cost is that the person running anvil can set them, which SECURITY.md says.
- **The binary's SHA-256 is computed once per process** from `std::env::current_exe()`, in 64 KiB reads, and is `unknown` if the file cannot be read.
- **Prompts and arguments are redacted before they are kept, in both modes.** The digest is of the redacted text, the same text the provider received; `full` keeps that text. `DataGuard::scrub` redacts without adding to the redaction count, so a model request's `redactions` counts only what entered the conversation since the previous request.
- **Tool results are recorded by SHA-256 of the redacted full output.** `OutputStats` gained `sha256` and `exit_code`; the FNV digest the usage records use stays.
- **File changes come from the tools that write.** `write_file` and `edit_file` return a `FileChange` with the SHA-256 before (none for a new file) and after; the loop, chat and delegated runs emit `LoopEvent::FileChanged` after the call's `ToolFinished`. Changes made by shell commands are not observed; that is in "What is not enforced" and on the roadmap.
- **Subagents report through `SubagentEnv::events`.** The default drops everything, so `anvil-compat` keeps no knowledge of the audit; the CLI's wiring returns a sink whose tap writes under the agent's name. A delegated turn is recorded as role `worker` on the provider that serves that role, and the decisions its registry makes are recorded under `main`, because the permission observer is shared and does not know which registry asked.
- **`anvil purge` and `retention_days` delete a session's audit file with its folder.** Retention is the administrator's choice and the mirror is untouched; keeping audit files past their transcripts would need a second retention setting nobody asked for.
- **The memory summarizer's request is a `model_request` too.** It goes through the same gated provider, and it does not run after an audit failure.

## Phase 5: review fixes

- **File tools redact the whole file before they choose lines.** `read_file` and `grep` run `Redactor::redact_lines` over each file's full text, then cut out or match lines in the result, so a key block is redacted whichever of its lines is asked for and a pattern can never match a secret. `redact_lines` puts as many line breaks after a marker as the match held, so line numbers and offsets stay right. The counts cover the whole file read (for `grep`, every file with a match), shown or not; counting more is the restrictive side.
- **A PEM-style body is redacted without its header.** The new kind `private_key_body` matches 3 or more consecutive lines of 60 to 76 base64 characters (an optional shorter last line joins the match). It is not scanned for by `anvil scan-keys`, for the same reason as `private_key`. The false-positive risk: any block of three or more long base64-alphabet lines is replaced, such as an embedded certificate, a base64 image in a text file, or a column of 64-character hex digests with nothing else on the line. That is accepted; it costs the model the text, never a secret.
- **SSH key files of every type are refused.** `id_ecdsa*` and `id_dsa*` joined the secret prefixes; the `_sk` forms (`id_ecdsa_sk`, `id_ed25519_sk`) match the existing prefixes.
- **The AWS key id shape has no word boundary.** `(AKIA|ASIA)[0-9A-Z]{16}` now matches inside a longer word, such as `_xAKIA...y`. The cost is a marker in the middle of a long uppercase identifier that happens to contain `AKIA` and 16 more capitals or digits.
- **Every log line is redacted at the sink.** Both log sinks write through a redacting writer in `anvil-cli/src/logging.rs`, instead of each call site redacting its field: hook output, MCP server stderr, provider error bodies and git output reach the log from many places, and one choke point cannot be forgotten by a new one. The writer starts with the built-in shapes and the secret-looking environment values (the `.env` files are loaded before logging starts) and switches to the session's redactor when the wiring builds it. Environment values are also matched in their JSON-escaped form, since the file sink writes JSON. A policy that turns redaction off does not turn it off for the log: the switch is about what the model sees, and the log never needs raw values.
- **Chat writes `redacted` records like the loop.** Chat keeps no transcript, so its session folder gains a `session.jsonl` only when a redaction happens and the transcript mode is not `off`; it holds the meta record (task `(chat: only redaction counts are kept)`) and `redacted` records for user lines, tool results and Stop hook reasons. `anvil resume` refuses a session whose log kept no conversation.
- **A `metadata` transcript keeps the final status by kind and code.** Provider error bodies and messages, transport, refusal and malformed details, and an unexpected-state detail become `(not kept: N bytes)`; the HTTP status, the API error kind, attempt counts and budgets stay.
- **Marker escaping matches on normalized text.** Before matching, zero-width characters and the soft hyphen are removed and fullwidth ASCII, small-form and other `<`, `/` and dash lookalikes are mapped to ASCII; the pattern is `<`, `&lt;` or a numeric entity of `<`, an optional `/`, then `untrusted`, up to three separators of any kind and `data`, in any case. The leading character of each match is escaped in the original text: `<` and its lookalikes become `&lt;`, the `&` of an entity becomes `&amp;`, so an escaped marker never matches again. Escaping every `untrusted ... data` word instead was the other choice; it would change ordinary prose and source text (this repository's own) that the model may need to edit exactly.
- **A chat Stop hook's reason goes in as delimited hook output.** It was sent as a plain user turn; it is now redacted and wrapped with source `hook`, the same as hook output in a tool result.
- **The MCP listing digest covers every field the client acts on.** Each tool is hashed as `{name, title, description, input_schema, annotations}`, with the annotations object hashed whole (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`, `title` and anything a server adds), so a flipped `readOnlyHint`, which decides whether a call runs without a prompt and in Plan, is a changed listing. Every approval recorded before this change no longer matches; the next listing is recorded again (unmanaged) or as the first one (managed).
- **Approvals are keyed by server name and a definition digest.** The definition digest covers the command and arguments of a local server or the URL of an HTTP one; the environment and headers are left out, since they carry settings and keys rather than what runs. Unmanaged, a changed definition keeps no approval and its first listing is recorded afresh. Under a policy, a changed definition is refused like a changed listing. Approvals an earlier version wrote (a bare digest without a definition) no longer count.
- **The MCP tool cache is gone; every start lists live.** The brief allowed dropping it if simpler. A cache that may only be used when it equals the live listing can only save the listing call, and it needs the connection either way, so it bought nothing. `ServerReport::from_cache` and the `refresh` argument of `McpTools::load` went with it. Old `~/.anvil/mcp-cache/` folders are left in place and never read.
- **Under a policy only the administrator accepts a listing.** A `[features] mcp_servers` entry may carry `listing_sha256` (64 hex digits, checked when the policy loads); then only that listing loads. Without a pin the first listing is recorded and any later change, or a changed definition, is refused with an error that prints the new digest and names `listing_sha256` and `[features] mcp_servers`. `anvil mcp approve` is refused under any policy, even for a server the policy allows. `anvil mcp list` prints `listing_sha256 = "<digest>"` for every server that answered, accepted or not, so the administrator can review and pin it. `anvil policy show` prints the pin as part of the entry.
- **Copies stay runnable.** `private_fs::copy` sets 0600, or 0700 when the source is executable by its owner, so a script saved in a template or installed with a skill still runs. Saved templates (`~/.anvil/templates/`) and installed skills (both scopes; their folders already were 0700) are copied this way; `anvil new` copies into the user's project with the user's umask, as before.
- **Reused files and folders are narrowed.** `private_fs::create_dir_all` narrows an existing folder to 0700 (the folder itself, not existing parents, which may be the user's); every append and write path, and the direct opens of the session log, status lock and temporary file, usage records, audit log and memory facts, narrow the file to 0600. A file or folder an earlier version or the user left wider is fixed on first use without a message: `anvil-types` has no logging, and the change only removes access.
- **The git index is narrowed after each git call.** Git writes `sessions/<id>/git-index` through a lock file and a rename with the umask's mode, so anvil cannot create it owner-only in advance; `snapshot_tree` sets 0600 after `git add` and after `git write-tree`, before any later step reads it. Between git's rename and the chmod the file has git's mode inside a 0700 folder, so no one else can reach it.
- **The Windows check counts inherit-only entries, whatever their rights.** An allow entry with the `IO` flag for anyone but the owner, SYSTEM, Administrators, OWNER RIGHTS or CREATOR OWNER fails the row, read rights included, because new files in the folder inherit it. The brief named write rights; counting any right is the restrictive side and matches the rule for direct entries. The check reads the folder's own descriptor, not each file in it. `[data] transcript_dir` and `[audit] mirror_dir` get their own rows when the policy sets them.
- **The memory summarizer's transcript gate moved into `finish_session`.** `memory::policy_skip_reason` returns why extraction must not run (memory off, or a transcript mode below `full`), and both `finish_session` (chat) and `remember` (runs) call it, so chat can no longer reach the summarizer below `full`.
- **Purge and retention skip a live folder and measure age by the newest file.** A session or build folder whose status lock a running process holds (`status::lock_is_free`, the same check `anvil status` uses) is never removed; an unreadable lock counts as held. A folder's age is the newest modification time of the folder or anything under it, links not followed, because appending to `session.jsonl` does not change the folder's own time.
- **Build folders are pruned with sessions.** `anvil purge` and `retention_days` also remove `<project>/.anvil/builds/<id>/` folders, by the same name, lock and age rules; a build holds a status lock in its folder while it runs, which decides whether it is live. Retention covers builds too, since a build folder holds item titles and acceptance commands the administrator asked to expire. `.anvil/builds/` joined `.gitignore` and the guidance in SECURITY.md.
- **Repositories get an id with a digest.** `trust::repo_id` is the canonical path's slug (letters and digits, other characters `-`, the last 64 kept) plus `-` and the first 12 hex digits of the SHA-256 of the canonical path. It names the folder under `transcript_dir`, the saved-rules file under `~/.anvil/permissions/` and the key in `~/.anvil/trust.toml`. `trust::repo_key`, the canonical path itself, stays for comparing paths (the MCP approval scope); it was never lossy, but the trust file now uses the id like the rest, as the brief decided. Old trust records and saved rules no longer apply, so the user is asked again; old `transcript_dir` folders are not moved, and purge of the new folder does not reach them. CHANGELOG.md says so.
- **The redaction-off note is checked by its text and its call.** The note is a constant, `REDACTION_OFF_NOTE`, and the test checks that the policy turns the guard off and that `with_policy` prints that constant; capturing the process's stderr from a unit test is not possible without a second process, and no integration test can install a policy at its fixed system path.

## Phase 6: review fixes

- **Worked in the `D:\Coding\anvil-fix6` worktree** on `enterprise/fix6`, because the Phase 5 fixes were being committed in the main checkout at the same time.
- **The canonical form is enforced, not only described.** `chain::open_line` serializes the parsed record again and requires the same bytes as the line. Before, the hash covered the raw line, so a resealed line with an extra field, a `\u` escape, a space or reordered fields verified, and two verifiers could read one line differently. Now each record has exactly one valid line. The alternative, hashing a re-serialization instead of the line, would have kept many valid lines per record.
- **The Python check is a file with a test, not a snippet.** `crates/anvil-audit/src/audit/verify_audit.py` reads bytes, accepts LF only, requires the final segment to be empty, refuses duplicate keys through `object_pairs_hook`, checks the top-level fields, every event's fields and types and the order of the `roles` and `flags` maps, and compares `json.dumps(..., separators=(",", ":"), ensure_ascii=False)` with the line. `tests/python_check.rs` runs it and `verify` over 27 intact and tampered files, one record of every event type included, and requires the same verdict; it is skipped when no Python 3 is on the PATH. The old snippet read text mode (CRLF passed), dropped a cut last line silently and took the last of duplicate keys. The "cannot disagree" sentence is now backed by that test.
- **A mirror always holds the whole chain.** `AuditLog::open` compares the mirror with the verified session file. A missing or empty mirror first gets a copy of the session file, so one added on resume verifies on its own. A mirror with other bytes stops a required log with `AuditError::MirrorDiffers`; unrequired, it is a warning and appending goes on. Refusing was chosen over copying in that case: a mirror that differs is the evidence the mirror exists for, and overwriting it would destroy it.
- **`anvil audit verify --mirror <file>` compares byte for byte** and exits 1 naming the first differing line. For a session id under a policy with `mirror_dir` the copy there is compared without the flag, and a missing copy is a failure, since the policy says one is written.
- **A removed, replaced, cut or appended-to log file is a failed write.** Each file output remembers the length it wrote and, on Unix, its device and inode, and checks them before every append. On Windows the file is also opened with share mode `FILE_SHARE_READ` through the safe `OpenOptionsExt::share_mode`, so while a session runs other programs can read it but not delete, rename or write it. Before, a deleted file was written through the orphaned handle and nothing noticed.
- **The gate is checked again after the permission decision is recorded,** before the `PreToolUse` hook and again before `tool.run`, and in `ToolRegistry::permit`. The decision is the first record a call can fail to write after its `tool_call`, and the tool ran when that write failed. The `PostToolUse` hook is skipped once the gate is closed.
- **Every hook is gated.** `HookRunner::with_gate` refuses each command once the gate gives a reason: a `PreToolUse` hook then blocks its tool with that reason, and `SessionStart`, `PostToolUse` and `Stop` run nothing and report nothing (a refused `Stop` never asks the loop to continue). `Wiring::hook_runner` attaches the wiring's gate, and chat now calls `observe_permissions` before its first hook, where it used to run `SessionStart` hooks before the gate existed.
- **An `always` answer is scope `saved`.** `DecisionScope::Saved` is reported when the rule was added; when the policy forbids saving, or saving fails, the answer is `session`, as it acts. The usage records keep `session` for both, so their schema does not change. The fallback origin for a `Deny` with no matching rule is now `builtin_rule`; no tool's default is `Deny` today, so that path is not reached and has no test.
- **A build has its own audit log for acceptance decisions.** `Env::open_build_log` opens `.anvil/builds/<id>/audit.jsonl` (and `<mirror_dir>/<build id>.audit.jsonl`) when the build starts running items, with a `session_start` of mode `build`; each acceptance and project check decision goes there with its source, and `session_end` names how the build ended. `Wiring::permit_shell` takes the log to report to and otherwise reports nowhere, so a decision never lands in an item log after its `session_end` again. Recording under the item before its end was rejected: the command is chosen and checked by the build, after the item's session is over. A required build log that cannot be written stops the build before its first item; once it is running, a failed write refuses the next acceptance command. The planner's request still comes before the build id exists and stays outside every log. The build log lives in the build folder, so purge and `retention_days` treat it as the Phase 5 fixes treat build folders: it goes with its folder by the same age rule, never while the build's status lock is held (the log is opened after the build's status reporter and closed before it finishes), and the mirror copy stays.

The tool now searches a copy of the file with every CRLF turned into LF and maps each match back to the original bytes, so only the matched span is rewritten. Tabs, spaces and indentation still have to match, because they carry meaning in Python, Makefiles and YAML; the ticket's suggestion to normalize white space in general was not taken.
- **A replacement takes the ending of the first line it touches.** That is the first line break at or after the match's start. A match on a last line with no break takes the break before it, and a file with no break at all gets LF. In a mixed file the other lines keep their own endings.
- **An exact byte match is the fallback.** When the line-ending-insensitive search finds nothing, the old exact search runs, so an old text that ends in a lone `\r` (splitting a CRLF on purpose) still applies, with the new text inserted as given.
- **A match that is unique only by its line ending is ambiguous.** In a file with both `x\r\n` and `x\n`, the old text `x\n` now matches twice and is refused without `replace_all`. The model cannot see line endings, so it could not have meant one of them.
- **The byte order mark is outside the match.** It is kept whatever the edit, and an old text that starts with one (copied from line 1 of `read_file`'s output, where it is invisible) has it removed, with the new text's, before matching.
- **The not-found error checks white space first.** A white-space-only difference would also trip the first-line branch, so the more specific diagnosis comes first: the line where the old text matches with leading and trailing white space ignored, the first line that differs, and both versions with `·` for a space and `→` for a tab between `|` marks. Next, the old text's first non-blank line: its first occurrence, up to five further line numbers, and the file's lines for the region the old text would cover. Otherwise it says nothing similar was found and to read the file again. The limits are 20 lines, 160 characters a line and 4096 bytes.
- **The not-found error is redacted like `read_file`.** The lines it shows come from a copy of the whole file redacted first, because a region can start in the middle of a key block, where the registry's redactor on the result alone would miss the body lines. The counts are recorded and returned with the result, as `read_file` does.
- **`write_file` converts only one case.** It writes CRLF when the existing file uses CRLF throughout (at least one line break) and the new content has a line break and no CRLF. New files, LF and mixed files, and content that has any CRLF are written as given. Its result says when it converted. A byte order mark is not added or kept by `write_file`; the brief covered line endings only.
- **The edit preview goes through the tools' own functions.** `proposed_edit` calls `edit_file::apply` and `write_file::content_to_write`, so the diff shown before a write is what the tool will write. An ambiguous call the tool refuses now has no preview; it used to preview the first occurrence. `edit_file_previews_the_replacement` was changed to match.
- **Argument errors are read from the tool's schema.** serde names a missing field but not a field of the wrong type. `parse_args` now walks the same JSON schema the model received and names each argument at fault (`files[0].path` for nested ones), what it was and what it accepts, then lists the accepted arguments. No dependency such as `serde_path_to_error` was added. An unknown argument is mentioned only when parsing failed, since serde ignores it otherwise.
- **An offset past the end and a limit of 0 are still results, not errors.** `read_file` returned them as ordinary output before, and a multi-file read should not fail for one range. The messages now name the argument and the accepted range. Making them errors would change their audit outcome.
- **The end-to-end test proves the copy instead of computing it.** The fake provider's script is fixed before the run, so the test cannot build the edit from the live `read_file` result. It writes the old text as `read_file` shows it and asserts, from the session transcript, that the text is in what `read_file` returned with the line numbers removed, that the one `edit_file` call succeeded, and that every line of the file is still CRLF.

## Windows edit fixes: environment, transcript rows and session approvals

- **The environment section follows the base prompt, before the state prompt.** Plan and Build share everything up to the state heading, so placing the section there keeps the cached prefix the same across states. It is built from the session's `ToolContext` (the configured `Shell` and the `Runner`) and from whether `shell` is registered, so it cannot change within a session.
- **One sentence, `shell_fact`, feeds both the prompt and the tool description.** The wiring re-registers `shell` with that description whenever the mode is not `off`. The registry built without wiring (`ToolRegistry::with_builtins`, used by tests) keeps a description that names no single shell, so the tool list snapshot is the same on Windows and Linux.
- **Direct start is told whenever the runner starts programs directly, not only in allowlist mode.** A `shell_programs` rule also turns direct start on, and the model needs to know pipes fail there too. The existing "Shell allowlist" section, which lists the patterns, is unchanged.
- **The container executor is described as `sh` in a Linux container whatever the host.** That is what `run_command` starts there, so telling the model about PowerShell on a Windows host would be wrong.
- **The shell is named by its file name only.** Both `/` and `\` count as separators on every platform, so a Windows path in `tools.shell` never passes whole on Linux either.
- **Only known POSIX shells are called POSIX.** `sh`, `bash`, `dash`, `zsh`, `ksh` and `ash` are; any other program is "the shell the configuration names", because anvil cannot know its syntax.
- **Subagents get the fact through the tool description only.** Their prompt is the agent's own body, not the base prompt, and their tool list already shows each description.
- **The loop request snapshot masks the environment section.** It names the platform's shell, which differs between the Windows and Linux runners; the section's own snapshots pin each variant.
- **The `cancelled tool` rows were results that overtook their start event.** The TUI's tool hook (`ResultTee`) sends each result straight to the UI's message channel, while `ToolStarted` and `ToolFinished` first pass the usage task (`SessionUsage::sink`, which also writes `status.json`) and then the event channel; `run_ui` picks among ready channels at random. A result that arrived first made a placeholder row named `tool`, the start event then added a second row, and the finish event closed only that second one. When the turn ended, `cancel_running` (called on every `Busy(false)`, not only on a cancel) marked the stranded placeholder cancelled, with the seconds since the result as its duration. The fix is in the transcript, not in the channels: the start event now fills in a placeholder with the same call id, so the order of arrival no longer matters, and the result message carries the tool name so a row is never nameless. Merging the two channels was rejected because the hook runs inside the registry, which has no handle on the loop's event sink.
- **The session-approval test goes through the CLI wiring, and no code changed.** The registry and the loop already had tests for a "session" answer (`session_approval_stops_later_edit_prompts_inside_the_root`, `session_approval_survives_compaction_and_a_retried_call`). The new test, `a_session_answer_holds_for_later_edits_in_the_same_session`, covers what they do not: the registries a real unmanaged session gets from `Wiring`, the session's and a subagent's, with paths written relative, with `./` and absolute. It passed on the existing code, so the ticket's report is not reproduced and nothing else changed. It covers the unmanaged default only; a policy's `allow_always` changes what `always` saves, not whether "session" holds.

## Windows edit fixes: line-ending review

- **An overlapping second match makes `old` ambiguous.** `match_indices` skips matches that overlap the first, so `\n\n` in a file with three blank line breaks counted once and was applied at a guessed place. Uniqueness now counts overlapping matches; `replace_all` still replaces the non-overlapping matches from the left, as `str::replace` does.
- **A CRLF in `old` may be a line's own `\r` before an LF break.** `read_file` shows a line that ends `\r\r\n` as `x\r`, so a model copies it as `x\r` plus LF, which normalizing `old` turned into `x\n`. When the normalized `old` finds nothing, `old` is tried as written against the normalized file before the exact byte match. An `old` that mixes both readings of `\r\n` still does not match; that needs backtracking and is not worth it for such files.
- **An `old` that starts with a byte order mark matches only at the start of a file that has one.** Stripping the mark and searching everywhere let it match the same text in the middle of the file, or in a file with no mark, which is a difference other than line endings.
- **The not-found message splits lines at LF only.** `str::lines` drops a `\r` before each break, so a trailing `\r` could never be shown and the message printed lines identical to the old text. The `visible` helper already marked `\r`; it now gets the chance.
- **The preview parses arguments with the tools' own types.** It read `replace_all` leniently, so `"replace_all": "yes"` showed an edit that the tool then refused to make.
- **In a mixed file, new text takes the ending of the first line it replaces.** Matching endings line by line is not defined when `new` has a different number of lines than `old`, so the existing rule stays.
