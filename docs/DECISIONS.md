# Decisions

Choices made while hardening anvil for regulated, restricted-network environments, each with the reason. Where two options were reasonable, the more restrictive one was taken. Newest phase last.

## Taken with the repository owner before the run

- **The work continues on `enterprise/hardening` and draft pull request #43.** The branch already held the first round of hardening (removals, repository trust, the file jail, the scrubbed child environment, one HTTP module, the managed policy). Starting again from `main` would have redone that work for no gain.
- **The Ticket schema leaves anvil.** `anvil-types` no longer has `Ticket`, its validator, `ticket::dirs` or the `--schema` binary. The separate repository that consumed the ticket schema still imports them at a pinned commit, so it keeps building; before it moves its pin past this branch it must copy `Ticket` and `ticket::dirs` into its own types crate. Nothing in this repository was changed to accommodate it.
- **This plan overrides the decisions of 2026-11-17 where they conflict.** herdr reporting is deleted rather than kept behind a policy switch. HTTP MCP servers come back only behind the network allowlist of a later phase. Provider tolerance for self-hosted servers and the `anvil doctor` acceptance test stay on the roadmap.

## Phase 1: removals

- **`classify.rs` and `signal.rs` are removed with ticket drafting.** Their only consumer was `anvil ticket draft`: the session end classified records into `signals.jsonl`, and nothing else read that file. `anvil stats` reads the records directly and is unaffected.
- **The `[telemetry]` table is removed.** It only held the thresholds that turned statistics into ticket signals.
- **A configuration that still sets a removed table fails to load.** `[tickets]`, `[telemetry]` and `[integrations]` join `[update]` and `[notify]`: anvil stops and names the table and why it is gone, instead of ignoring it. Silently ignoring it would let someone believe a feature is still on.
- **`anvil memory` is gone, not only `anvil memory learn`.** `learn` was its only subcommand. Facts and standing rules stay and are reached as before (the end-of-session proposals, `rule: <text>`, `anvil rules`).
- **The managed policy's `summarizer_calls` now covers one call.** With the start-of-session rule proposals deleted, it switches only the end-of-session memory summarizer.
- **`anvil setup` writes one example provider named `endpoint`.** It is the same name `anvil setup --endpoint` writes, so running that command replaces the example in place. The example URL is `https://models.internal.example/v1`: the `.example` domain is reserved and never resolves, so an unedited example cannot reach a real host, and it uses https so it passes the egress rules unchanged. Its key variable is `ANVIL_ENDPOINT_KEY`. Under a managed policy, `anvil setup` without `--endpoint` is still refused, because the example would not be on the policy's allowlist.
- **`anvil config init --global` writes the same single example.** The template used to describe a rented GPU behind a vendor's proxy, which is a hosted service; it now describes a server on the organization's own network.
- **Hosted APIs are documented, never written.** The Anthropic and OpenAI protocol adapters stay, and README.md shows one hosted provider entry for a user who adds it by hand.
- **The build commit is read at compile time, without a build script.** `anvil --version` prints `<version> (<commit>)` when the release build sets `ANVIL_BUILD_SHA`, and the version alone for a build from source. A build script would run code at build time for no extra benefit. The release workflow has to set the variable; that change belongs to the supply chain phase.
- **`anvil scan-keys` still reads a repository's `.anvil/.env`.** It never loads it into the environment; it reads the values only to fail when one of them appears in a tracked file. Nothing a repository ships can set an environment variable of anvil.
- **The old-name check has no exceptions.** With the migration module gone, `just no-old-name` and the CI step search the whole tree. The CI step was edited in place, ahead of the supply chain phase, because leaving the exceptions would have pointed at files that no longer exist.
- **An MCP definition may only reference variables a child receives.** `${VAR}` in an MCP server's `command`, `args` and `env` used to read anvil's whole environment, so a trusted repository's `.mcp.json` could copy a provider key loaded from `~/.anvil/.env` into its server. Expansion now draws only from the child environment allowlist plus `[tools] pass_env`. A reference to any other variable is an error that stops that server and names the variable, rather than expanding to empty: an empty value would start the server in a state the user did not intend and hide why. The check runs when the server is started, after `[tools] pass_env` is known, and applies to the user's own `~/.anvil/mcp.toml` as well, because the risk is the same whoever wrote the file. The trust prompt now shows each definition as written, including its environment entries, and never an expanded value.

## Phase 2: managed policy

- **One path per system, and macOS uses `/etc/anvil`.** The plan names `/etc/anvil/policy.toml` for Linux and macOS, so the former `/Library/Application Support/Anvil` path is gone. Windows uses the literal `C:\ProgramData\anvil\policy.toml` rather than `%ProgramData%`: an environment variable is a lower layer the user controls, so reading the path from one would let the user move the policy.
- **Windows ownership is read as SDDL from `Get-Acl`, not from `icacls`.** `icacls` prints principals by localized name, so a German or Japanese Windows would need its own list of group names. `icacls /save` gives security identifiers but writes them to a file, which would have to sit in a folder the user can write while anvil reads it back. `Get-Acl` prints SDDL with security identifiers on stdout. PowerShell is started by its full path under `C:\Windows\System32` with a cleared environment and `-NoProfile`, because the user being constrained controls `PATH`, `PSModulePath` and their profile. Unknown SDDL is a failure, not a pass.
- **Ownership checks treat delete and change-permission as write.** Deleting the policy file would put anvil back into unmanaged mode, and the right to change permissions or ownership leads to write access, so each of these counts as a right only administrators may hold. Administrators, SYSTEM and TrustedInstaller are accepted; `CREATOR OWNER` entries are ignored because they only describe what new child objects get.
- **The ownership check does not run in `anvil policy check` unless `--ownership` is given.** An administrator validates a draft in a working folder before it is installed; requiring root ownership there would make the command useless in a pipeline.
- **The policy is schema version 1 and lists only keys that are enforced now.** CA bundle, client certificate and proxy (Phase 4), HTTP MCP hosts (Phase 4), `[shell]` (Phase 3), redaction and transcript modes (Phase 5) and `[audit]` (Phase 6) are added by those phases. Until then a policy that names them is refused as an unknown key, which is the safe failure. `policies/restricted.toml` gains the shell allowlist and the required audit sink in those phases.
- **The forced profile is replaced by policy `deny` and `ask` lists.** A profile file next to the policy was a second file to own and check; two lists in the policy say the same thing in one place. `--profile` is no longer refused under a policy: a profile is a lower layer like the user's configuration, and anything in it that conflicts with the policy is an error naming the key.
- **`allow_skip_prompts` is split into `allow_yes`, `allow_allow_tool` and `allow_always`.** The plan asks for each switch separately, and an organization may reasonably allow pre-approving one tool while forbidding `--yes`.
- **A user `allow` rule conflicts with a policy rule when it names the same tool and the policy rule has no pattern or the same pattern.** Deciding whether two arbitrary globs overlap is not reliable; this rule catches the cases a person would write by hand and is explained in the error. The policy's rules are added on top of the user's in every case (`Permissions::tighten`), so an allow rule the check does not catch still cannot loosen a policy `deny` or `ask`.
- **A saved `always` rules file is an error when `allow_always = false`.** Reading it would let rules saved before the policy was installed stay in force; ignoring it silently would break the rule that conflicts are never ignored. The error names the file so the user can delete it.
- **Conflicts in anvil's own files are errors; items from files shared with Claude Code or a repository are left out with a note.** (Replaced for `~/.claude` in "Phase 2: review fixes".) `~/.anvil/settings.json`, `~/.anvil/mcp.toml` and `~/.anvil/skills` are anvil's configuration, so a hook, server or skill there that the policy forbids stops anvil with the policy key. `~/.claude/...` files belong to another tool the developer may use alongside anvil, and a repository's files are its content, not the user's configuration; refusing to start because they exist would make anvil unusable next to Claude Code. They are not loaded, and a note names the policy key.
- **MCP allowlist entries name both the server and its program.** A name alone can be reused by any definition, and a program alone can be started with any arguments under a trusted name; requiring both matches the plan's "named servers" without trusting the name by itself.
- **`[features] skills = "bundled"` means the skills shipped next to the source tree.** A release binary carries no bundled skills folder today, so on most machines `bundled` loads nothing; it exists so a policy can say "no third-party skills" without turning skills off for source builds.
- **`[features] memory` covers facts and the end-of-session summarizer, not standing rules.** Rules live in `~/.anvil/rules.toml`, outside `~/.anvil/memory`, are written only when the user types `rule:` or runs `anvil rules`, and never involve a model call. The former `[sessions] summarizer_calls` key is folded into `memory`.
- **`[projects] allow_trust` defaults to `false`.** It is the more restrictive choice. A repository's `deny` and `ask` rules still apply without trust, because they only tighten; the former `[project] config = false`, which also dropped those rules, is gone.
- **`[files] extra_roots` are read-only, and the user's `[tools] extra_dirs` is an error under a policy.** The plan calls them readable roots, and a user folder outside the workspace is exactly what an organization would want to decide centrally.
- **Session token ceilings cap the default silently and refuse an explicit excess.** The built-in default (2,000,000) is not a setting anyone chose, so lowering it to the ceiling is not overriding a lower layer; a value the user wrote is, so it is an error. The same holds for `anvil build` caps.
- **`policy: unmanaged` goes to stderr with the line renderer.** Its stdout stays byte-identical for scripts. The full-screen UI shows the same fact as a `policy` row on its startup screen.
- **The policy hash is the SHA-256 of the file's bytes.** `anvil_types::policy::label` returns `sha256:<hex>` or `unmanaged` for the audit records of Phase 6.
- **The test that shows an environment variable cannot escape the policy works through `home_dir_from`.** `std::env::set_var` is `unsafe` in Rust 2024 and the workspace forbids `unsafe`, so the test passes the value `ANVIL_HOME` would have to the same function `home_dir` uses.

## Phase 7: supply chain and releases

- **`actions/attest` instead of `actions/attest-build-provenance`.** The latter's README says that since v4 it is a wrapper around `actions/attest` and that new workflows should use `actions/attest` directly. Both were at v4.2.2 when checked (2026-11-19).
- **No `artifact-metadata: write` for the release.** The `actions/attest` README lists it, but only for the storage record it creates when `push-to-registry` is set, which anvil does not use. Leaving it out keeps the release to three write scopes: `contents`, `id-token`, `attestations`.
- **Write scopes at the top of `release.yml`, narrowed per job.** The permission test reads the top-level block, so the union of what the release needs is declared there and each build job narrows itself to `contents: read`. The test now also refuses any job-level block that grants more than `read` or `none`, so a job cannot widen the grant unnoticed.
- **`cargo deny` is installed with `cargo install --locked` in CI, not through `EmbarkStudios/cargo-deny-action`.** The action runs a Docker image that downloads the cargo-deny binary without a checksum and uses an older Rust image than `rust-toolchain.toml`. Building the pinned version (0.22.0) from crates.io with its own lockfile keeps one less third-party component in CI, at the cost of about two minutes per run.
- **chrono's unmaintained advisory is ignored with a reason.** RUSTSEC-2026-0543 marks `chrono` unmaintained with no safe upgrade. It reports no vulnerability. Replacing chrono with `jiff` or `time` touches every crate and is a roadmap item, not part of this phase.
- **The workspace crates are `publish = false`.** anvil ships binaries only. Without it, cargo-deny treats the path dependencies between workspace crates as wildcard versions of publishable crates and fails the `wildcards = "deny"` rule.
- **One SBOM for the anvil binary, all targets.** `cargo cyclonedx --target all` lists the dependencies of every platform in one CycloneDX 1.5 file, which is simpler for a reviewer than one file per target and never omits a platform-specific crate.
- **No build cache in the release workflow.** `Swatinem/rust-cache` was removed from `release.yml` so a release is built from a clean state; CI keeps the cache.
- **Release notes come from `CHANGELOG.md`.** The release job fails when the tagged version has no section, so a tag cannot publish without a changelog entry.
- **`aarch64-apple-darwin` added, `x86_64-apple-darwin` not.** The `macos-14` runner is Apple silicon and builds natively; an Intel build would need cross-compilation or a deprecated runner.

## Phase 2: project trust

- **Loosening keys in a repository's `.anvil/config.toml` are errors, not warnings.** The plan says such a file "may not" change providers, roles, the shell program or allow rules. An error that names the key is more restrictive than ignoring it, and it tells the developer the repository is trying something, instead of letting them believe a setting is active. The error covers `[providers]`, `[roles]`, `[tools]` (shell, check, `pass_env`, `extra_dirs`), `[network]`, and `allow`, `default` and `allow_tools` under `[permissions]`. Other unknown keys are still ignored with a warning, as decided on 2026-11-17, because they change nothing.
- **A repository's `allow` rules live only in `.anvil/permissions.toml`, and wait for trust.** `default` and `allow_tools` stay errors there: a default would allow everything unnamed, and pre-approval would skip prompts for a whole tool.
- **A trusted repository's `allow` is the weakest rule.** It decides only a call that no `deny`, `ask` or `allow` of the user's or the repository's matches and that the user's own `default` does not cover. It replaces the tool's built-in default and nothing else, and it never lifts the blocked-command list or `shell_programs`. This keeps the user's explicit choices above anything the repository says.
- **What the trust digest covers.** `.anvil/permissions.toml`, `.anvil/settings.json` and `.local`, `.claude/settings.json` and `.local`, `.mcp.json`, `ANVIL.md`, `CLAUDE.md`, `CLAUDE.local.md`, `.claude/CLAUDE.md`, every `CLAUDE.md` in a subfolder (found honoring `.gitignore`), the instruction text as anvil loads it (so a changed `@import` target counts), and every file under `.claude/skills`, `.claude/commands`, `.claude/agents`, `.anvil/skills`, `.anvil/commands` and `.anvil/agents` (skill scripts included). Each file enters with its relative path, so adding, removing or renaming one changes the digest. `.anvil/config.toml` is left out: it can only tighten.
- **A refusal is not pinned.** "Do not trust" stays whatever the repository changes, because it loosens nothing; only a decision to trust is tied to content.
- **Trust recorded before digests existed no longer counts.** The old `trust.toml` format still loads, but a bare `trusted` entry is treated as undecided, so the user is asked once more. A bare `untrusted` entry still counts.
- **Writes to files that grant power are refused, not asked about.** Before this phase a write to a hook settings file asked a person. The plan says tools may never write these files, so the prompt path is gone: `.anvil/config.toml`, `.anvil/permissions.toml`, any `settings*.json` in a `.claude` or `.anvil` folder, `.mcp.json`, and everything under `~/.anvil` are refused by `ToolContext::checked_path` before any rule is consulted. The match ignores letter case on every system, which on Linux also refuses names anvil would not read; that costs nothing and avoids a case-folding mistake on Windows and macOS.
- **One path decides trust, with the policy switch as a parameter.** `trust::decide` and `trust::run` take `allow_trust`, and the CLI always passes `anvil_types::policy::allows_project_trust(policy)` (`true` in unmanaged mode). When it is `false`, nothing is asked or recorded, a stored trust is ignored, and `anvil trust` (without `--revoke`) is an error.

## Phase 2: review fixes

- **Only a missing policy is unmanaged.** `load_checked` used `Path::exists`, which is `false` for any error, so a policy folder the user may not list ran anvil unmanaged. The file's `symlink_metadata` must now say not found, and its folder must be not found or a folder; any other error (permission denied, a folder that is a file) stops anvil with the reason. A policy folder that exists while the file does not is still unmanaged, because an empty `/etc/anvil` is an ordinary state and the file lookup inside a folder the user may not list already fails with permission denied.
- **`default = "allow"` counts as `--yes`.** It approves every call no rule names without a person, so under `allow_yes = false` it is an error naming that key wherever a user layer sets it: the configuration, a profile, or the saved rules file under `~/.anvil/permissions/`. A repository's files could already not set `default`. No other route approves an unnamed call: rules name one tool, and there is no wildcard tool.
- **Forbidden items in `~/.claude` are errors, like `~/.anvil`.** The plan says a conflict is never ignored silently, and both folders are the user's own configuration. The cost: a developer with Claude Code hooks, MCP servers or skills in `~/.claude` that the policy forbids cannot start anvil until they remove them or the administrator allows them. The error names the policy key and the file.
- **Forbidden items a trusted repository ships stay a visible note.** An error would make every trusted repository with a `.mcp.json`, hooks or skills unusable under a policy that turns those off, and the developer cannot fix it without editing the repository. The note on stderr names the policy key and the file, so it is not silent; the item never loads.
