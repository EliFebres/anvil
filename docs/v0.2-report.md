# Anvil v0.2 report

All six phases are built on `dev`. No phase is blocked. No paid eval run was made: the provider API keys were not in the environment, so every measurement the phases asked for is left as a command under "What Eli must do by hand". `docs/v0.2-progress.md` has the per-phase plans and the full decision lists.

## How the checks were run

Smart App Control on the development machine blocks `just.exe` and, at times, binaries built into `target/`. The steps of `just check` were run by hand with `CARGO_TARGET_DIR` in a temporary directory, and this pull request was opened early as a draft so CI runs the real `just check` on Ubuntu and Windows, plus the selftest, on every push. CI caught one bug the local run could not: a new snapshot had recorded CRLF from the prompt files on Windows and failed on Ubuntu (fixed in `e7d1ff3`).

Implementation was delegated to Sonnet helpers in herdr panes; planning, briefs and review stayed in the main session.

## Phase 1: factory cost fixes

**Changed.**

- Gate order is A (`just check`), C (review swarm), then the release build and B (eval). A change the reviewers send back never pays for a build or an eval. After a Gate B failure the new diff goes through A and C again.
- `[eval_gate] paths` in `factory.toml`: Gate B and the release build run only when a changed path matches. This repository lists the `anvil-*` crates, `crates/eval/**`, `skills/**`, `eval/tasks/**`, `Cargo.toml`, `Cargo.lock` and `rust-toolchain.toml`. A skipped gate is recorded as `B: eval` skipped with the reason.
- Fix rounds get a narrow task: the change is already on the branch, here are the findings, address each and nothing else.
- A failed reviewer is rerun alone, up to two more passes 30 seconds apart. One that still fails pauses the ticket; no implementer run and no review round is spent.
- `blocking` on each `[[reviewers]]` entry, true by default for correctness and safety only. Findings of a non-blocking reviewer are always comments. The style prompt no longer rates anything `major` "because it fails the build".
- Cost and weighted tokens per implementer run, Gate B run and Gate C round, in the notes, the pull request body, `outcomes.jsonl` and `status.json`.

**Decisions.** Fix rounds use option (b), a fresh session with a narrow task: `anvil resume` takes no new instruction and the factory does not capture the session id. A reviewer that cannot be reached returns `Outcome::Paused`, which pauses the service as every other pause does; the ticket is reopened, not lost. "Do not undo an earlier fix" stays in the reviewer prompt's `earlier_findings`.

**Measured.** Nothing; the phase needed no eval.

## Phase 2: planner, builder and reviewer roles

**Changed.**

- `[roles] planner` is optional. With a planner on a different provider, Plan runs on it and Build starts a new coder conversation seeded with the task and the approved plan. Without one, every request is byte-identical to before; a request snapshot written before the loop changed proves it.
- Escalation: two failed project checks in a row, or two review change requests, send the next Build round to the planner, then the loop returns to the coder. Each one emits an event and a summary line.
- Spend per role in the loop result, telemetry, `anvil stats` and the status line, each role priced with its own provider. The breakdown is shown only when a planner or a worker is configured.
- Eval results record the provider and model of every role per attempt. Schema version 2; schema 1 still reads; the top-level `model` stays the coder's.
- Config surface: commented `planner` lines in the templates, `planner` as a role name for `--model` and agent definitions, the planner in `/model` and doctor.
- Factory: `[roles] planner` in `factory.toml` and the profile. A reviewer must differ from the coder in base URL or model, so an expensive model may review a cheap one from the same vendor. The blocking reviewers must cover at least two models.

**Decisions.** The planner is `None` inside the loop unless it names a different provider than the coder. Escalation counters count consecutive failures and are not restored on resume. `summary.md` shows tokens per role, not cost, because the core has no prices. `/model <name>` still switches only the coder.

**Measured.** Nothing; see the two commands below.

## Phase 3: cheap workers

**Changed.**

- `[roles] worker`, optional, defaulting to the coder; an agent definition's `model` may name it.
- Two built-in agents, `explore` (read-only) and `implement` (write tools and the shell under the session's permission rules). Both default to the worker role; a project or user agent with the same name overrides them.
- Several `delegate` calls in one turn run at the same time, at most four, when the target agent has only read tools. Calls to an agent that may write run one after another. Results and events keep call order.
- A short Delegation section in the Plan and Build prompts when the tool is offered; `[prompt] delegate_guidance = false` turns it off.
- Delegated turns are booked under the worker role, recorded in telemetry, and draw on the session budget.
- While planning, a delegated call that may write is refused.

**Decisions.** The loop asks a generic `Tool::parallel_safe`, so anvil-core still knows nothing of anvil-compat. `implement` reaches the owner's permission prompt through a new agent key, `permissions: inherit`; it grants nothing the session lacks. An agent whose `model` names another provider is still priced at the worker's price, because the turn event carries only the role. Compaction inside a subagent counts as a worker turn.

**One thing to know.** Because the built-in agents always exist, `delegate` is registered in every session and the system prompt now lists `explore` and `implement`. That changes the prompt for every run, so the next eval baseline will not be comparable turn for turn with the one on `main`.

**Measured.** Nothing. The phase's rule was: if workers make cost worse and pass rate no better, turn the guidance off by default. That comparison is not done, so `delegate_guidance` is on by default and the command to decide it is below.

## Phase 4: session status signal

**Changed.**

- Every `run`, `resume` and `chat` writes `status.json` in its session directory, atomically: `working`, `needs_input`, `blocked`, `done` or `failed`, with the loop state, a one-line detail and the spend.
- `anvil status` lists the project's sessions newest first; `--json`; `--all`. A session recorded as working whose process is gone shows as `stale`.
- `[notify] webhook_env`: one message on entering `needs_input`, `blocked`, `done` or `failed`.
- `[integrations] herdr = true`: reports the same states to herdr through its documented CLI.

**Decisions.** Liveness is a lock on `status.lock` held by the session (`File::try_lock`), which raised `rust-version` from 1.88 to 1.89. `--all` reads a new registry, `~/.anvil/projects/<hash>`, so sessions from before this change are not listed until the project runs again. The notification sender is a second small implementation; the crate boundaries forbid sharing the factory's. Herdr was built because its documentation gives the pane identity (`HERDR_PANE_ID`). An idle chat waiting for the next message stays `working`.

## Phase 5: learning how I work

**Changed.**

- Rules reach the prompt by relevance: the rules for the languages present in the project, `*` rules, and rules for languages that cannot be detected.
- Corrections: at the end of a session anvil records the files it changed. At the next session start, and on `anvil memory learn`, the files edited afterwards are diffed and the summarizer proposes rules through the existing keep or drop flow.
- Templates: `anvil template save <name> [dir]`, `anvil new <template> <dir>`, and a template list in the prompt when a task starts in an empty directory.

**Decisions.** The reviewer gets the same rule set as the coder: the changed files are not known where the sections are built. Corrections store a capped copy of the text rather than using git, so uncommitted work is covered. Under `--yes` the proposal step is skipped and `anvil memory learn` picks the edits up later. Proposals carry no mechanical check; the text says when one is realistic.

## Phase 6: long builds

**Changed.**

- `anvil build <spec.md>`: the planner writes an ordered list of work items, each with an acceptance command, under `.anvil/builds/<id>/`. The list is approved like a session plan.
- One fresh session per item through the normal loop. An item is done only when its acceptance command and the project check exit 0; then it is committed with the item's title.
- `anvil build resume [id]` and `anvil build status [id]`.
- `--budget-usd` and `--budget-tokens` cap the build. An item that fails twice stops the build as `needs_input`, with the tree clean and each failed attempt on a side branch.

**Decisions.** `.anvil/` is excluded from the clean-tree check and from build commits, so the spec file must be committed or live outside the repository. Inside a build each item's plan is approved at once and the memory prompts are skipped. Because the checks decide, a session that stopped early but whose checks pass is committed as done. Session approvals granted during one item carry into later items.

## What Eli must do by hand

### 1. Config for a planner, coder and worker split

`~/.anvil/config.toml` (provider names are yours; `price_per_mtoken` on each makes the per-role cost appear):

```toml
[roles]
planner = "opus"        # plans, and takes a Build round when the coder is stuck
coder = "sonnet"        # builds
worker = "haiku"        # the explore and implement agents
reviewer = "opus"
summarizer = "haiku"

# Optional
[notify]
webhook_env = "ANVIL_WEBHOOK_URL"

[integrations]
herdr = true
```

Factory: in `factory.toml` add `planner = "<provider>"` under `[roles]`, and the same line in the profile `deploy/nuc/anvil-factory.toml` (a test requires the two to agree). Reviewers may now sit on the coder's vendor as long as the model differs.

### 2. Update the factory on the NUC

After this pull request is merged:

```
ssh nuc
factory update
```

`factory update` pauses, waits for the ticket in progress, pulls `main`, rebuilds `anvil` and `factory` and the worker image, and restarts. It must run before the next ticket: `factory.toml` has new keys (`[eval_gate]`, `blocking`) and the eval result schema is now 2, which the old binary cannot read once a new baseline lands.

### 3. Record a new eval baseline

The system prompt changed for every session (the built-in agents), so record a baseline before trusting Gate B again:

```
eval baseline
```

It runs every task three times on the factory's coder and commits the one result file. Earlier full runs at three repeats cost about $10 to $26.

### 4. Paid eval runs that were skipped

`eval run` always writes to `eval/results/`; move each file to `docs/data/` afterwards so the factory does not gate against a partial result.

Phase 2, planner and coder on the same model, then a cheaper coder (six tasks, three of them `large`; about $1.40, then an estimated $0.60 to $0.90):

```
eval run --provider opus  --tags large,fix-test,errors --repeat 1 --anvil-bin target/release/anvil
eval run --provider haiku --tags large,fix-test,errors --repeat 1 --anvil-bin target/release/anvil
```

Both need `[roles]` with `coder`, `planner`, `reviewer` and `summarizer` set to `"opus"` and a `haiku` provider on the same vendor.

Phase 3, the `large` tasks with the built-in agents (about $1.14 per run on Opus), once with `[prompt] delegate_guidance = true` and once with `false`:

```
eval run --tags large --repeat 1 --anvil-bin target/release/anvil
```

If the run with guidance costs more and passes no more often, set `delegate_guidance` to default `false` in `crates/anvil-types/src/config.rs`.

## Ideas not built

- Factory: drawing per-gate costs in `factory watch`; pausing only the affected ticket when a reviewer cannot be reached; gate costs on a paused outcome.
- Eval: an `--out` flag for `eval run`; a planner override flag.
- Roles: budgets per role; a cost line in `summary.md`; restoring escalation counters on resume; pricing a delegated turn by the provider that served it.
- Workers: parallel runs of non-adjacent read-only delegations; a cap on delegated runs per session.
- Status: `anvil status --watch`; webhook retries; rate limiting repeated `needs_input` messages; listing builds in `anvil status`.
- Learning: rule proposals with a structured check; nested `.gitignore` files; `anvil template list` and `remove`; reviewer rules filtered by the changed files.
- Builds: parallel work items; `--json` for `anvil build status`; editing items after approval; a Ctrl-C handler that records `blocked`; an untracked spec file.
