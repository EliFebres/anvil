# Security notes

This page is for someone deciding whether anvil may run on their machines. It describes what the code in this repository does, with file references, so each claim can be checked. If you find a vulnerability, open a private security advisory on the GitHub repository rather than a public issue.

## In one paragraph

anvil is a single binary on the developer's machine. It never runs a model: it sends prompts, and the files and command output its tools read, over HTTPS to the model endpoints configured in the user's own `~/.anvil/config.toml`, and to nothing else unless the user turns something on. It has no telemetry upload, no self-update, no update check and no background process. A repository it runs in can only make it stricter, and the hooks, MCP servers, skills and instruction files a repository ships load only after the user trusts it. Its file tools stay inside the project and never open credential stores; the programs it starts do not inherit API keys. An administrator can install a managed policy that limits all of this further and that the user cannot override. **A shell command the user approves runs with the user's own rights; anvil does not sandbox it at the operating system level.**

## Who is responsible for what

- **anvil** is responsible for what it does on the developer's machine: which files its tools open, what the programs it starts inherit and may run, which servers it talks to, and what a cloned repository may change. Everything below is enforced in-process, in the same way on Windows, macOS and Linux.
- **The model host** (an internal model server, a rented GPU, or an API vendor) is responsible for that machine: its patching, network exposure, authentication, logging and retention of prompts, and who can read what it receives. anvil sends it the task, the instruction files, the files and command output the tools read, and the conversation so far. Treat everything a session reads as sent to the host.
- **The firm** decides who may run anvil, on which repositories, with which policy, and what wraps it (an operating system sandbox, a separate account, endpoint monitoring, review of every change through pull requests). `docs/enterprise/pilot-scope.md` is a template for a first pilot.

## What is not enforced

- **Approved shell commands are not sandboxed.** They run with the user's rights, can read any file the user can read and reach any host the user can reach. The file jail applies to anvil's file tools, not to programs a command starts. `shell_programs` narrows what may start, but an allowed program can still run code it is given (`cargo build` runs build scripts, `just` runs recipes, `npm test` runs scripts). Operating system sandboxing is on the roadmap (`docs/ROADMAP.md`) and can be added around anvil today.
- **Everything a session reads goes to the model host.** There is no redaction of secrets inside file contents or command output before they are sent or written to the transcript; the credential-store deny list keeps the file tools away from the usual places, but a secret in an ordinary source file is sent like any other text. Redaction is on the roadmap.
- **Trust is per repository path, not per content.** A trusted repository can change its hooks or instruction files later and the new versions load. Pinning with re-approval on change is on the roadmap.
- **The substring blocklist** (`rm -rf`, `Remove-Item -Recurse`, `git push --force`, `git reset --hard`) is a second layer and is easy to get around; it is not a control.
- **Binaries are not code-signed** with a publisher certificate. Releases carry checksums, an SBOM and build provenance attestations instead; see "Release builds".
- **The API key sits in the user's environment or `~/.anvil/.env`**, protected by file permissions, not by an operating system credential store.
- **Transcripts are plain files** without an append-only or hash-chained audit log.

## Network destinations

Every HTTP request anvil makes goes to a model endpoint, through a client built in one function, `http_client` in `crates/anvil-core/src/net.rs`. That client does not follow redirects, so a server cannot pass a request on to another host. Before a provider is used, `Egress::check` decides whether its `base_url` may be called: it must use https unless the host is loopback or listed in `[network] allow_http_hosts` in the user's own configuration, and under a managed policy its `host:port` must be one of the policy's `[network] allowed_hosts`, and plain http is accepted only to loopback unless the policy sets `require_tls = false`. Under a policy, a provider in the user's configuration whose host is not allowed stops anvil at startup with an error naming `[network] allowed_hosts`, and `[network] allow_http_hosts` in the user's configuration is an error naming `[network] require_tls`. A refused endpoint gets no request, and the refusal is logged.

## Files anvil writes

Nothing anvil records leaves the machine. There is no upload code.

| what | where | content |
|---|---|---|
| Session transcripts | `<project>/.anvil/sessions/<id>/`, or under a policy's `transcript_dir` (one subfolder per repository) | `session.jsonl` holds the full conversation, including file contents and command output the tools returned; `tool-output/` the untruncated outputs; `status.json` the session's state. Kept until deleted, or for the policy's `retention_days`. |
| Usage records | `<project>/.anvil/telemetry/<date>.jsonl` and a copy in `~/.anvil/telemetry/` | Content-free: provider, model, tokens, latency, retries, stop reasons, tool names with argument and result sizes and digests, permission decisions, check results by program name and command digest, provider error kinds. The project path is stored as a digest. |
| Logs | `<project>/.anvil/logs/` | Structured logs; `ANVIL_LOG` sets the level. Requests are logged by URL and attempt, never with headers. |
| Memory and rules | `~/.anvil/memory/`, `~/.anvil/rules.toml` | Facts and rules the user chose to keep. |
| Trust decisions | `~/.anvil/trust.toml` | Each repository path the user answered the trust prompt for, and the answer. |

The `.gitignore` of this repository keeps `.anvil/telemetry/`, `.anvil/sessions/`, `.anvil/logs/` and `.anvil/mcp-cache/` out of commits; other projects need the same lines.

## API keys

- Each provider names the environment variable that holds its key (`api_key_env`); the key is read from the process environment when the provider is built (`crates/anvil-core/src/provider/mod.rs`). Keys never appear in configuration files.
- At startup anvil fills the environment from `~/.anvil/.env` without overriding anything already set (`crates/anvil-types/src/dotenv.rs`). A repository's `.anvil/.env` is never loaded, so a repository cannot set a key, `ANVIL_HOME`, a proxy or any other variable.
- Provider definitions, and so the variable a key is read from and the URL it is sent to, come only from the user's own configuration or profile; a repository cannot name them.
- The key goes only to the endpoint of the provider that names it. It is not written to logs or transcripts, and an error body that repeats it is redacted.
- Programs anvil starts (shell commands, checks, hooks, MCP servers, rule checks) do not receive the key; see "What anvil's tools can reach".
- `anvil setup` writes `~/.anvil/.env` from placeholders and makes it private: mode 600 on Unix; on Windows it inspects the ACL with `icacls` and prints the command that removes a grant to other users (`crates/anvil-cli/src/setup.rs`).
- `anvil scan-keys` (part of `just check` and CI) fails when a tracked file holds something shaped like a key (`sk-`, `AIza`, `ghp_`, `github_pat_`, `hf_`) or any value of 12 or more characters from the user's `.env` files; it reports the file and line, never the value (`crates/anvil-cli/src/secrets.rs`).

## Permissions

- Every tool call is decided by the user's own rules: the `[permissions]` table of `~/.anvil/config.toml` or of a `--profile`, or else the user's file for the repository, `~/.anvil/permissions/<repository>.toml` (`crates/anvil-core/src/tools/permissions.rs`, `Wiring::user_permissions`). A managed policy adds its own `deny` and `ask` rules on top of every other layer, and a user or profile `allow` rule that one of them covers is an error. The repository adds its `deny`, `ask` and `shell_programs` from `.anvil/config.toml` and `.anvil/permissions.toml`; it cannot add `allow` rules or a `default`.
- A rule is `tool` or `tool:glob`; the glob matches the path for file tools and the command line for `shell`. A `deny` from any layer wins, then a repository or policy `ask`, then the user's `allow`, then the user's `ask`, then the `default`, then the tool's own default.
- Without rules, reading tools (`read_file`, `glob`, `grep`, `list_dir`, `outline`, `delegate`, `skill`, read-only MCP tools) run; `write_file`, `edit_file`, `shell` and every other MCP tool ask.
- `shell_programs`, when any layer sets it, limits a `shell` call to one program from the list, named as found on `PATH`, with plain arguments: `&&`, `||`, `;`, `|`, `&`, `>`, `<`, backticks, `$(`, `${`, `@(`, `(` and line breaks are refused, covering sh, PowerShell and cmd. No rule, answer or `--yes` lifts it, and each layer can only narrow the list (`Permissions::shell_refusal`). `profiles/strict.toml` ships it with `default = "ask"`; copy it to `~/.anvil/profiles/` and run with `--profile strict`, or have the policy force it.
- The substring blocklist (`rm -rf`, `Remove-Item -Recurse`, `git push --force`, `git reset --hard`) refuses those commands even under `--yes` unless an `allow` rule names them (`crates/anvil-core/src/tools/shell.rs`). It is a second layer, not the control.
- A prompt offers yes (this call), no, session (this tool for the rest of the session; for path tools only inside the project root, symlinks resolved) and, for `shell` only, always (saves `shell:<first word> *` to the user's own file for the repository, never into the repository).
- `--yes` answers every prompt with yes and approves plans; deny rules, `shell_programs` and the blocklist still apply. One kind of call is never approved without a person: a `write_file` or `edit_file` to `settings.json` or `settings.local.json` in a `.claude` or `.anvil` folder, the files that define hooks. A hook written there would run in a later session without any prompt, so such a write always asks, even when an allow rule, a profile, `--allow-tool` or `permissions.allow_tools` covers the tool. Under `--yes`, or with no one to answer, it is refused. A `session` or `always` answer covers that one call only and saves nothing. A deny rule still refuses it without asking. `--allow-tool <name>` and `permissions.allow_tools` pre-approve a tool for one session. Under a managed policy `--yes` is refused unless `allow_yes = true`, `--allow-tool` and `permissions.allow_tools` unless `allow_allow_tool = true`, and the `always` answer saves nothing unless `allow_always = true`; the policy can also require a person to approve plans (see `require_plan_approval` below for exactly which).
- In the Plan state a tool that may write is refused. The Verify state runs the project's check: a command the user set in `[tools] check` runs as set; a command anvil detects from the repository's files (`just check`, `cargo test`, `npm test`, `python -m pytest`) runs the repository's own code, so it is asked about like any `shell` call.

## What anvil's tools can reach

- **Files.** Every file tool (`read_file`, `write_file`, `edit_file`, `glob`, `grep`, `list_dir`, `outline`) resolves its path, symlinks and `..` included, before opening it, and refuses anything outside the project root, the session folder and the folders listed in `[tools] extra_dirs`; installed skill folders may be read (`ToolContext::checked_path`, `crates/anvil-core/src/tools/workspace.rs`). Wherever they are, `.env` and `.env.*` files (not `.env.example`), `.ssh`, `.aws`, `.azure`, `.config/gcloud`, `.kube`, `.docker/config.json`, `.gnupg`, `.netrc`, `.git-credentials`, `~/.anvil/.env`, Chrome, Edge and Firefox profiles, and the macOS, Linux and Windows keychains and credential stores are refused, and directory searches skip them. Writes are also refused inside any git directory (`inside_git_dir`): a `.git` folder or file at any depth, which covers the git directories of worktrees and submodules under the main `.git`, and any folder git itself would take for a git directory because it holds `HEAD`, `objects` and `refs` (a bare repository, or one made with `--separate-git-dir`). A tool can therefore not plant a hook, change `.git/config` or `.git/info/attributes`, or repoint a worktree. Reading `.git` stays allowed.
- **Environment.** Programs anvil starts for the model or the repository (`shell` commands, check commands, hooks, MCP servers, rule checks) do not inherit anvil's environment. They receive `PATH`, the home, user and temp variables, the locale (`LANG`, `LC_*` without secret-looking names), `TERM`, `NO_COLOR`, the variables Windows needs to start programs (`SystemRoot`, `windir`, `ComSpec`, `PATHEXT`, `SystemDrive`, `HOMEDRIVE`, `HOMEPATH`, `APPDATA`, `LOCALAPPDATA`, `ProgramData`, the `ProgramFiles` and `CommonProgramFiles` folders, `NUMBER_OF_PROCESSORS`, `PROCESSOR_ARCHITECTURE`, `PROCESSOR_IDENTIFIER`, `OS`, `PSModulePath`), `CARGO_HOME` and `RUSTUP_HOME`, and the names listed in `[tools] pass_env` (`crates/anvil-types/src/child_env.rs`). Provider keys and tokens are not passed. An MCP server definition (the user's or a trusted repository's) may set extra variables for its server, and its `command`, `args` and `env` may use `${VAR}`, but only for a variable from that same list: a reference to any other variable, such as a provider key, stops that server from starting with an error that names the variable (`McpServer::launch` in `crates/anvil-compat/src/mcp/mod.rs`; tests `a_definition_cannot_copy_a_withheld_variable_into_a_server`, `a_launch_expands_only_variables_children_receive`).
- **anvil's own git calls.** anvil runs git in the project itself to snapshot and diff a session's changes, to commit the items of `anvil build`, and to list changed files for `anvil rules check` and tracked files for `anvil scan-keys`. The model does not choose these commands, and they keep the user's full environment, because git needs the user's identity and settings. The repository's own config (`.git/config`, what it includes, `config.worktree`) is not the user's, so every one of these calls goes through `anvil_core::git::command` (`crates/anvil-core/src/git.rs`), which passes these as `-c` settings, which beat every config file:
  - `core.hooksPath=/dev/null`: no hook runs, including on build commits and checkouts (the user's own hooks in `.git/hooks` do not run on these commits either);
  - `core.fsmonitor=false`: no file system monitor program;
  - `--no-pager`, `core.editor=:` and `sequence.editor=:`: no pager or editor (git treats `:` as no editor);
  - `protocol.allow=never`: no remote is contacted, so `core.sshCommand`, credential helpers and proxies never run.

  Diffs also pass `--no-ext-diff --no-textconv`, so `diff.external` and the diff drivers named in `.gitattributes` never run. Aliases need nothing: git never lets an alias replace a built-in command, and anvil runs built-in commands only. Clean and smudge filters and commit signing programs cannot be switched off from the command line without also switching off the user's own (Git LFS, a signing key). So when the repository's own config names one (`filter.<name>.clean`, `smudge` or `process`, `gpg.program` or `gpg.<format>.program`), anvil refuses to run git there and names the key to remove; the same keys in the user's or the system's config are the user's choice and are used. This needs git 2.26 or later (`git config --show-scope`). A test fails the build if non-test code starts git in any other way.
- **Not confined.** An approved `shell` command, see "What is not enforced".

## Running in a repository you do not trust

A repository you clone cannot change how anvil treats you:

- Its `.anvil/config.toml` and `.anvil/permissions.toml` may only add `deny`, `ask` and `shell_programs`. Every other key (providers, `base_url`, roles, limits, `[tools] shell` and `check`, `allow`, `default`, `allow_tools`) is ignored with a warning that names it (`crates/anvil-types/src/project.rs`).
- Its `.anvil/.env` is never loaded.
- Its hooks, MCP servers, skills, slash commands, agents and instruction files (`ANVIL.md`, `CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md`, nested `CLAUDE.md` files) do not load until the user trusts the repository (`crates/anvil-cli/src/trust.rs`). The first interactive session lists every item, with the command line of each hook and MCP server and every variable an MCP server definition sets, exactly as written in the file (`${VAR}` references are shown, not expanded), and asks once. The answer is kept in `~/.anvil/trust.toml`, keyed by the repository's full path. With `--plain`, `--yes`, no terminal, or a command that never prompts (`doctor`, `build`), an undecided repository is untrusted: nothing it ships loads and nothing is recorded. `anvil trust` shows the list and asks again; `anvil trust --revoke` withdraws trust. Under a managed policy a repository can be trusted only when `[projects] allow_trust = true`; otherwise nothing it ships loads, whatever the user decided, and its `deny` and `ask` rules still apply.
- Even in a trusted repository, an `@path` import in one of its instruction files may only name a file inside the repository, so a `CLAUDE.md` cannot pull `~/.ssh/...` into the prompt (`crates/anvil-compat/src/instructions.rs`).

## Managed policy

An administrator can install a policy file that nothing below it can loosen (`crates/anvil-types/src/policy/mod.rs`, `crates/anvil-types/src/policy/ownership.rs`, `crates/anvil-cli/src/policy.rs`). `policies/restricted.toml` and `policies/standard.toml` are commented examples, and `docs/ADMIN_GUIDE.md` lists every key with its default.

- **Location.** `/etc/anvil/policy.toml` on Linux and macOS, `C:\ProgramData\anvil\policy.toml` on Windows (`system_path`). The path is a literal in the binary: no environment variable, flag, profile or configuration key moves it or turns it off, and the Windows path is not read from `%ProgramData%`, which a user can change for their own processes. Tests pass another path as a function argument. Test: `the_system_path_is_fixed_per_system`.
- **Ownership.** Before the file is read, `ownership::check` makes sure only an administrator can change it. On Unix the file and its folder must be owned by root and not writable by group or others. On Windows the owner of each must be Administrators, SYSTEM or TrustedInstaller, and no access-control entry may give anyone else a right that writes, deletes or takes over either; the access list is read as SDDL from `Get-Acl` (security identifiers, not localized names), with PowerShell started by its full path, a cleared environment and no profile. A file that fails the check stops anvil with the reason. Tests: `a_policy_file_with_bad_ownership_stops_anvil` (a file the test user created is refused), `unix_needs_root_and_no_group_or_other_write`, `a_user_owned_or_user_writable_descriptor_fails`, `unreadable_descriptors_fail_closed`. Note that a folder created under `C:\ProgramData` inherits a grant that lets Users create files, so the administrator must remove inheritance (`docs/ADMIN_GUIDE.md` has the command).
- **Failure.** A policy file that exists but is not safely owned, cannot be read, does not parse, has an unknown key, names another `version` than 1, or breaks one of its own rules stops anvil before it does anything else, with the reason. Test: `broken_policies_are_errors`.
- **Unmanaged mode.** Without a policy file anvil runs unmanaged. Every session prints `policy: unmanaged` (on stderr with the line renderer, as the `policy` row of the full-screen startup screen), and `anvil doctor` shows it as a skipped `policy` row. With a policy it prints `policy: managed (<path>, sha256:<hash>)`. Tests: `show_and_report_name_each_setting_and_its_layer`, `policy_rows_show_presence_ownership_and_hash`.
- **Precedence.** The policy outranks the user's configuration, a `--profile`, environment variables (a home chosen through `ANVIL_HOME` is checked like any other), command-line flags and the repository. A lower layer that conflicts with it is an error that names the policy key and the setting, never a silent override (`check_flags`, `check_config`, `check_build` in `crates/anvil-cli/src/policy.rs`, `Wiring::with_policy`). One exception is deliberate: hooks, MCP servers and skills defined in files shared with Claude Code (`~/.claude/...`) or shipped by a trusted repository are not anvil's configuration, so when the policy forbids them they are left out with a note naming the policy key instead of stopping anvil. The same items defined in anvil's own files under `~/.anvil` are errors. Tests: every test in `crates/anvil-cli/src/wiring/policy_tests.rs`, including `a_profile_cannot_loosen_the_policy`, `a_home_chosen_through_anvil_home_is_still_under_the_policy`, `the_users_own_hooks_conflict_and_shared_or_project_hooks_do_not_load` and `mcp_servers_need_the_mode_and_a_matching_name_and_program`; `skip_flags_are_refused_with_the_policy_key`; `a_user_configuration_that_conflicts_with_the_policy_stops_the_session` in `main.rs`.
- **Keys.** Every key except `version` and `[network] allowed_hosts` defaults to the restrictive choice.
  - `version = 1`: required.
  - `[network] allowed_hosts`: the only `host:port` pairs a provider may name; required. `require_tls` (default `true`): plain http only to loopback.
  - `[models] providers`, `models`: the provider names and model names the configuration may use; empty means any.
  - `[permissions] deny`, `ask`: rules added on top of every other layer; a user or profile `allow` rule that the policy's `deny` or `ask` covers is an error. `allow_yes`, `allow_allow_tool` (default `false`): whether `--yes`, and `--allow-tool` or `permissions.allow_tools`, may be used. `allow_always` (default `false`): whether the `always` answer saves a rule and saved rules under `~/.anvil/permissions/` are read; when off the prompt does not offer it, an `always` answer counts for the session only, and a saved rules file is an error. `require_plan_approval` (default `false`): a person approves the plan of every `anvil run` and chat session, even under `--yes`; in `anvil build` it covers only the top-level build plan.
  - `[files] extra_roots`: folders outside the workspace the file tools may read, never write; `[tools] extra_dirs` in the user's configuration is an error under a policy. `deny`: path globs the file tools refuse and searches skip, on top of the built-in secret list, inside the workspace too.
  - `[features] mcp` (`off`, `allowlist` with `mcp_servers` entries that name both the server and its program, or `on`), `hooks`, `skills` (`off`, `bundled`, `local`), `memory` (when off nothing under `~/.anvil/memory` is read or written and the end-of-session summarizer does not run), `build` (`anvil build`), `delegation` (the `delegate` tool). All default to off.
  - `[projects] allow_trust` (default `false`): whether a repository can be trusted at all.
  - `[data] transcript_dir`, `retention_days`: where session folders go, and how many days they are kept; older ones are deleted when a session starts.
  - `[limits] session_tokens`, `build_tokens`, `build_usd`: ceilings. A larger value set by the user or a flag is an error; without one, the ceiling is used.
- **Subagents.** Delegated agents use the same registry rules, file limits and policy as the session. Test: `a_subagent_gets_the_same_policy_rules_and_file_limits`.
- **Commands.** `anvil policy show` prints every effective policy setting with the layer that set it (`policy` or `default`), then the user settings the policy bounds with theirs. `anvil policy check <file> [--ownership]` validates a file for an administrator before rollout and exits 1 with the reasons. `anvil doctor` has `policy`, `policy:ownership` and `policy:sha256` rows.
- **Where it is applied.** At startup in `crates/anvil-cli/src/main.rs` (loading, flags, configuration, `anvil build`, trust), and inside a session in one function, `Wiring::with_policy` in `crates/anvil-cli/src/wiring.rs`, plus `Wiring::registry` and `Wiring::tool_context`, which subagents share.
- **Not yet in the policy.** TLS client settings (CA bundle, client certificate, proxy), HTTP MCP servers, shell modes, redaction and transcript modes, and audit settings arrive in later work and are listed in `docs/ROADMAP.md` until they exist.

## Release builds

- **Trigger.** `.github/workflows/release.yml` runs only when a version tag (`v*`) is pushed; pushes to `main` publish nothing. A test in `crates/anvil-types/tests/workflows.rs` (`release_runs_only_on_version_tags_and_builds_locked`) fails if the trigger changes or a build drops `--locked`.
- **Builds.** `anvil-cli` is built in release mode with `--locked`, from a clean state without a build cache, on GitHub-hosted runners for `x86_64-unknown-linux-gnu`, `x86_64-unknown-linux-musl`, `x86_64-pc-windows-msvc` and `aarch64-apple-darwin`, with the toolchain pinned in `rust-toolchain.toml`.
- **Assets.** Besides the binaries, each release carries `SHA256SUMS`, `anvil.cdx.json` (a CycloneDX 1.5 SBOM of the anvil binary's dependencies for every platform, made with `cargo-cyclonedx`), and `anvil-<version>-vendored-src.tar.gz` (the tagged source with every dependency vendored, for an offline build; see "Building offline" in `README.md`). The release notes are the version's section of `CHANGELOG.md`.
- **Provenance.** Every asset listed in `SHA256SUMS` gets a GitHub artifact attestation (SLSA build provenance, signed through Sigstore) made by `actions/attest`. `gh attestation verify <file> --repo EliFebres/anvil` checks that a file was built by this repository's release workflow from the tagged commit. This proves where and how a file was built; it is not a code signature from a publisher's certificate, and Windows and macOS will still treat the binaries as unsigned.
- **Workflow permissions.** `release.yml` is the only workflow that may write, and only to `contents` (the release), `id-token` (the attestation's signing certificate) and `attestations`. Its build jobs narrow themselves to `contents: read`. `ci.yml` is read-only. `crates/anvil-types/tests/workflows.rs` refuses any other write grant, and any job-level block that widens instead of narrowing.
- **Pinned actions.** Every action is pinned to a full commit SHA with its version in a comment (`every_action_is_pinned_to_a_commit_sha`). Dependabot (`.github/dependabot.yml`) proposes updates to actions and Cargo dependencies as pull requests; nothing merges without review.
- **Dependency gate.** `cargo deny check` runs in CI (`ci.yml`, job `deny`) against `deny.toml`: every RustSec advisory fails the build unless listed with a reason (one is: `chrono` is unmaintained, with no known vulnerability), only the permissive licenses listed there are accepted, `openssl-sys`, `openssl` and `native-tls` are banned so TLS stays on rustls, and crates.io is the only allowed source. `just deny` runs the same check locally.
- **Ownership.** `.github/CODEOWNERS` requires the owner's review for every path.
- anvil has no self-update. A newer binary comes from whoever distributes anvil to the user.
