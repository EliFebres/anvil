# Security notes

This page is for someone deciding whether anvil may run on their machines. It describes what the code in this repository does, with file references, so each claim can be checked. If you find a vulnerability, open a private security advisory on the GitHub repository rather than a public issue.

## In one paragraph

anvil is a single binary on the developer's machine. It never runs a model: it sends prompts, and the files and command output its tools read, over HTTPS to the model endpoints configured in the user's own `~/.anvil/config.toml`, and to the HTTP MCP servers the user's files (or a trusted repository's) define, and to nothing else. It sends no usage data anywhere, and has no self-update, no update check and no background process. A repository it runs in can only make it stricter until the user trusts it; its hooks, MCP servers, skills, instruction files and `allow` rules take effect only after the user trusts that exact content, and any change asks again. No file tool can write the files that grant these powers. Its file tools stay inside the project and never open credential stores or key files; the programs it starts, git included, do not inherit API keys. Secret-shaped text in what the tools return is redacted before it is sent or stored, and that text reaches the model marked as data. The `shell` tool can be turned off, limited to an allowlist of commands started without a shell, or run in a container without network access. An administrator can install a managed policy that limits all of this further and that the user cannot override. **In the default `ask` mode on the host, a shell command the user approves runs with the user's own rights; anvil does not sandbox it at the operating system level, and its command-text checks are a guard rail, not a boundary.**

## Who is responsible for what

- **anvil** is responsible for what it does on the developer's machine: which files its tools open, what the programs it starts inherit and may run, which servers it talks to, and what a cloned repository may change. Everything below is enforced in-process, in the same way on Windows, macOS and Linux.
- **The model host** (an internal model server, a rented GPU, or an API vendor) is responsible for that machine: its patching, network exposure, authentication, logging and retention of prompts, and who can read what it receives. anvil sends it the task, the instruction files, the files and command output the tools read, and the conversation so far. Treat everything a session reads as sent to the host.
- **The firm** decides who may run anvil, on which repositories, with which policy, and what wraps it (an operating system sandbox, a separate account, endpoint monitoring, review of every change through pull requests). `docs/enterprise/pilot-scope.md` is a template for a first pilot.

## What is not enforced

- **Approved shell commands on the host are not sandboxed.** In `ask` and `allowlist` mode on the host they run with the user's rights, can read any file the user can read and reach any host the user can reach. The file boundary applies to anvil's file tools, not to programs a command starts. The deny categories match command text, so in `ask` mode a shell can hide a command from them (a variable, an alias, a script file): they are a guard rail, not a boundary. `allowlist` mode limits which programs start and with which arguments (no shell, no argument naming a path outside the project, no git option that changes config, writes a file or runs a program), but not what an allowed program then does: `cargo build` runs build scripts, `just` runs recipes and `npm test` runs scripts, all of which the model can write, and programs set in the user's own git config run. The container executor is the boundary for that. Operating system sandboxing on the host is on the roadmap (`docs/ROADMAP.md`).
- **The container executor relies on the container runtime.** anvil builds the arguments; the isolation is docker's or podman's. The image is whatever the configuration names, so pin it by digest. anvil runs it with `--pull=never`, so an image that is not already on the workstation is an error rather than a download; administrators pre-load it. Hooks and MCP servers are not run in the container.
- **Everything a session reads goes to the model host, and redaction only catches known shapes.** Redaction replaces the built-in key shapes (`sk-`, `AIza`, `ghp_`, `github_pat_`, `hf_` keys, AWS access key ids, PEM private key blocks and runs of three or more 60 to 76 character base64 lines that look like their bodies, JWTs), the exact values of environment variables whose names look secret or that a provider names as `api_key_env` (8 characters or more), and the policy's own patterns. A password in a configuration file, a connection string, customer data or a key in any other format is sent and stored like ordinary text, and so is a known key that is encoded (base64, URL escapes) or split across lines. The model's own messages and tool arguments are not redacted; they can only repeat what it was sent, which was redacted. A policy can turn redaction off (`[data] redaction = false`); anvil then prints a note and logs a warning (`the_redaction_off_note_is_printed_and_redaction_is_off` in `crates/anvil-cli/src/wiring/policy_tests.rs`).
- **The untrusted-data delimiters are a mitigation for prompt injection, not a guarantee.** They tell the model which text came from files, programs and servers. Content cannot close the block without the per-session nonce (a ULID: 80 random bits), and marker-like text inside it is escaped, but a model can still follow instructions it was told to treat as data, or misread an escaped marker. The permission rules, the file boundary and the shell modes are what limit the result.
- **MCP listing approvals detect a change the server makes, not one the user makes.** `~/.anvil/mcp-approvals.toml` is the user's file; editing or deleting it makes the next listing count as the first. A policy's `listing_sha256` pin does not depend on it.
- **Below `full`, the plan and summary stay.** In `metadata` and `off` transcript modes `plan.md` and `summary.md` are still written to the session folder (the plan is what the user approves, and the summary is printed at the end); `retention_days` and `anvil purge` remove them with the folder.
- **On Windows, files inherit their folder's access list.** anvil does not change access lists; `anvil doctor` reports a `.anvil`, `~/.anvil`, `transcript_dir` or `mirror_dir` folder that others can open, or whose entries pass access on to the files created in it, with the `icacls` command that fixes it. It checks the folder itself, not each file inside.
- **A shell command can still write the files that grant power.** The refusal above covers anvil's file tools only; it does not stop an approved shell command. An approved shell command, on the host in `ask` or `allowlist` mode or in the container executor (whose workspace mount is writable), can write, when its user may write there, `.anvil/permissions.toml`, `.mcp.json`, a script a hook runs, or `~/.anvil/config.toml` (for example `default = "allow"`, which then counts from the next session, or is refused at startup under a policy that forbids `--yes`). A change to a repository's files changes the trust digest, so a trusted repository is asked about again before the new content takes effect, but nothing stops the write itself. The shell modes narrow which commands can run (`allowlist` starts only listed programs, without a shell) and the container executor keeps `~/.anvil` out of reach, but neither looks at which files a command writes.
- **Hard links are not detected, for reads or writes.** A file tool resolves symbolic links and junctions, but a hard link is the same file under a second name, and the secret list and the protected-file checks look at names. If a hard link from an ordinary name to a protected or secret file exists (`fsutil hardlink create a.txt .anvil\permissions.toml`, `ln .env notes.txt`), a later `write_file a.txt` writes the protected file, and `read_file notes.txt` or `grep` reads the secret. A repository can also ship such a link only if its checkout tool creates hard links, which git does not. Creating the link takes an approved shell command, as above: in `allowlist` mode only when a listed program can make links, and in the container executor only inside the workspace.
- **Binaries are not code-signed** with a publisher certificate. Releases carry checksums, an SBOM and build provenance attestations instead; see "Release builds".
- **The API key sits in the user's environment or `~/.anvil/.env`**, protected by file permissions, not by an operating system credential store.
- **The audit chain cannot show its own end being cut, or a rewrite.** Each record names the hash of the one before, so an edited, removed or moved record inside `audit.jsonl` breaks the chain. Someone who can write the file can still cut records from the end, or rewrite the whole file and recompute every hash, and the result verifies. The policy's `[audit] mirror_dir` exists for that: point it at a folder the developer can append to but not rewrite, collect it, and compare. Without a mirror the log is evidence against accidents and casual edits, not against the machine's owner.
- **Changes a shell command makes are not in the audit log as file changes.** `file_change` records come from `write_file` and `edit_file`, with the SHA-256 before and after. A command run through `shell` is recorded as a tool call and result (with its exit code), not by the files it touched.
- **The user and host in audit records come from the environment.** They are `USERNAME` or `USER` and `COMPUTERNAME` or `HOSTNAME` (then `/etc/hostname`), which the person running anvil can set. The binary's SHA-256 is computed from the running file once per process.
- **Some activity is outside a session's audit log.** `anvil build` asks the planner for its work items before any session starts, and runs each item's acceptance command after its session ends; those are in the build's state, not an audit log. A permission decision made inside a subagent's registry is recorded under `main`; the subagent's own tool calls and results carry its name.

## Network destinations

Every HTTP request anvil makes goes to a model endpoint or an HTTP MCP server, through a client built in one function, `http_client` in `crates/anvil-core/src/net.rs`. That client does not follow redirects, so a server cannot pass a request on to another host, and it checks every request in `HttpRequest::send` before a connection is made:

- **Where.** In unmanaged mode a request may go only to a `host:port` that the user's configuration names: a provider `base_url`, or the `url` of an HTTP MCP server in `~/.anvil/mcp.toml` or, once the repository is trusted, in its `.mcp.json` or `.claude/settings*.json`. Under a managed policy it may go only to a pair in `[network] allowed_hosts`.
- **Plain http.** `http://` is accepted only for loopback (`localhost`, `127.0.0.0/8`, `::1`), unless the host is in `[network] allow_http_hosts` in the user's own configuration (unmanaged) or the policy sets `require_tls = false` (managed). Every provider's `base_url` is checked as soon as the configuration loads, for every command (`check_plain_http` in `crates/anvil-cli/src/main.rs`); every configured endpoint, HTTP MCP servers included, again when a session starts (`Wiring::check_endpoints`), so a refused one stops anvil with the reason; and every request when it is sent.
- **Keys.** An API key, and each header an HTTP MCP definition sets, is added after the URL is checked and only when the request's `host:port` is that of the URL it was configured with. A provider key echoed by its provider is redacted from the provider's errors.
- **Proxy and TLS.** No proxy is used unless the policy's `[network] proxy` says so: `HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY` and `NO_PROXY` are ignored in the default mode `none`; `system` uses them or the system settings; a URL sends every request through that proxy. The policy's `[network] ca_bundle` replaces the system trust store; `client_cert` and `client_key` are presented for mutual TLS. anvil reads these files when it builds the client and stores nothing.

Under a policy, a provider or HTTP MCP server in the user's configuration whose host is not allowed stops anvil at startup with an error naming `[network] allowed_hosts`, and `[network] allow_http_hosts` in the user's configuration is an error naming `[network] require_tls`. A refused request is not sent, and the refusal is logged. `anvil doctor --egress` lists every destination anvil's HTTP client can reach under the current configuration, what uses it, the endpoints the rules refuse, and the proxy and TLS settings, without sending anything. Local MCP servers, hooks and shell commands are programs that make their own connections; it does not list those (see the table).

## API keys

- Each provider names the environment variable that holds its key (`api_key_env`); the key is read from the process environment when the provider is built (`crates/anvil-core/src/provider/mod.rs`). Keys never appear in configuration files.
- At startup anvil fills the environment from `~/.anvil/.env` without overriding anything already set (`crates/anvil-types/src/dotenv.rs`). A repository's `.anvil/.env` is never loaded, so a repository cannot set a key, `ANVIL_HOME`, a proxy or any other variable.
- Under a policy that sets `[network] client_cert` and `client_key`, anvil reads that private key from the policy's absolute path each time it builds its HTTP client, and uses it only for the TLS handshake. The file tools refuse key and certificate files, so the model cannot read it.
- Provider definitions, and so the variable a key is read from and the URL it is sent to, come only from the user's own configuration or profile; a repository cannot name them.
- The key goes only to the endpoint of the provider that names it: it is added to a request only when the request's `host:port` is that of the provider's `base_url` (`HttpRequest::api_key`; test `an_api_key_never_reaches_another_host`). It is not written to logs or transcripts, and an error body that repeats it is redacted.
- Programs anvil starts (shell commands, checks, acceptance commands, hooks, MCP servers, rule checks, git) do not receive the key unless `[tools] pass_env` names its variable; see "What anvil's tools can reach".
- `anvil setup` writes `~/.anvil/.env` from placeholders and makes it private: mode 600 on Unix; on Windows it inspects the ACL with `icacls` and prints the command that removes a grant to other users (`crates/anvil-cli/src/setup.rs`).
- `anvil scan-keys` (part of `just check` and CI) fails when a tracked file holds something shaped like a key (`sk-`, `AIza`, `ghp_`, `github_pat_`, `hf_`, an AWS access key id or a JWT, the shapes redaction uses, from `crates/anvil-types/src/redact.rs`) or any value of 12 or more characters from the user's `.env` files; it reports the file and line, never the value (`crates/anvil-cli/src/secrets.rs`). Private key blocks are redacted but not scanned for, because a repository may commit test keys on purpose (this one does, for its TLS tests).

## Permissions

- Every tool call is decided by the user's own rules: the `[permissions]` table of `~/.anvil/config.toml` or of a `--profile`, or else the user's file for the repository, `~/.anvil/permissions/<repository>.toml` (`crates/anvil-core/src/tools/permissions.rs`, `Wiring::user_permissions`). A managed policy adds its own `deny` and `ask` rules on top of every other layer, and a user or profile `allow` rule that one of them covers is an error. The repository adds its `deny`, `ask` and `shell_programs` from `.anvil/config.toml` and `.anvil/permissions.toml`. Its `.anvil/permissions.toml` may also list `allow` rules, which apply only while the user trusts the repository (`Permissions::allow_from_project`). It can never set a `default` or pre-approve tools.
- A rule is `tool` or `tool:glob`; the glob matches the path for file tools and the command line for `shell`. A `deny` from any layer wins, then a repository or policy `ask`, then the user's `allow`, then the user's `ask`, then the user's `default`, then a trusted repository's `allow`, then the tool's own default. A repository's `allow` never lifts a deny category, an allowlist or a `shell_programs` limit (test `a_projects_allow_only_decides_what_no_other_rule_decides`).
- Without rules, reading tools (`read_file`, `glob`, `grep`, `list_dir`, `outline`, `delegate`, `skill`, read-only MCP tools) run; `write_file`, `edit_file`, `shell` and every other MCP tool ask.
- `shell_programs`, when any layer sets it, is one more allowlist layer (see "The shell" below): a `shell` call must be one program from the list with plain arguments, started without a shell. No rule, answer or `--yes` lifts it, and each layer can only narrow what the others allow (`Permissions::shell_refusal`). `profiles/strict.toml` sets `[shell] mode = "allowlist"` with `default = "ask"`; copy it to `~/.anvil/profiles/` and run with `--profile strict`, or have the policy set the mode.
- The built-in deny categories refuse network clients, git commands that reach or change remotes, package installs, privilege tools and four destructive patterns even under `--yes` unless a rule names the command (`deny_category` in `crates/anvil-core/src/tools/shell.rs`, `Permissions::allows_by_name`).
- A prompt offers yes (this call), no, session (this tool for the rest of the session; for path tools only inside the project root, symlinks resolved) and, for `shell` only, always (saves `shell:<first word> *` to the user's own file for the repository, never into the repository).
- `--yes` answers every prompt with yes and approves plans; deny rules, the shell mode and allowlist, the deny categories and the refusal to write files that grant power (see the table above) still apply. `--allow-tool <name>` and `permissions.allow_tools` pre-approve a tool for one session. Under a managed policy `--yes` is refused unless `allow_yes = true`, `--allow-tool` and `permissions.allow_tools` unless `allow_allow_tool = true`, and the `always` answer saves nothing unless `allow_always = true`; the policy can also require a person to approve plans (see `require_plan_approval` below for exactly which).
- In the Plan state a tool that may write is refused. The Verify state runs the project's check: a command the user set in `[tools] check` runs as set (under a policy it must fit the shell mode, or anvil does not start); a command anvil detects from the repository's files (`just check`, `cargo test`, `npm test`, `python -m pytest`) runs the repository's own code, so it is asked about like any `shell` call. Every check runs through the same runner as the `shell` tool: directly in allowlist mode, in the container with the container executor.
- `anvil build` runs each work item's acceptance command, which the planner wrote, and a detected check only after the same permission path as a model's `shell` call allows it (`Wiring::permit_shell`); with `--yes` an `ask` is answered yes, otherwise a person is asked.

## What anvil's tools can reach

- **Files.** Every file tool (`read_file`, `write_file`, `edit_file`, `glob`, `grep`, `list_dir`, `outline`) resolves its path, symlinks, `..`, junctions and letter case included, before opening it, refuses a path Windows would fold onto another name (a trailing dot or space on any name, or `:` after the drive prefix, so `server.pem.` and `jx./out.txt` are refused rather than opened as `server.pem` and `jx/out.txt`; tests `folded_names_are_refused_for_reads_and_searches_on_every_system` and `boundary_windows_folded_junction_names_are_refused` in `crates/anvil-core/src/tools/boundary_tests.rs`), and refuses anything outside the project root, the session folder and the folders listed in `[tools] extra_dirs` (unmanaged) or the policy's `[files] extra_roots` (read-only); installed skill folders may be read (`ToolContext::checked_path`, `crates/anvil-core/src/tools/workspace.rs`). It refuses; it never asks. Wherever they are, inside the workspace too, these are refused, and `glob`, `grep` and `list_dir` leave them out: `.env` and `.env.*` files (not `.env.example`, `.sample` or `.template`), `*.pem`, `*.key`, `*.pfx`, `*.p12`, `id_rsa*`, `id_ed25519*`, `credentials*`, `.netrc`, `.npmrc`, `.pypirc`, `.pgpass`, `.git-credentials`, a repository's `.git/config`, `.ssh`, `.aws`, `.azure`, `.config/gcloud`, `.kube`, `.docker/config.json`, `.gnupg`, `~/.anvil/.env`, Chrome, Edge and Firefox profiles, and the macOS, Linux and Windows keychains and credential stores. A policy's `[files] deny` globs are added to this list. Writes are also refused inside any git directory (`inside_git_dir`): a `.git` folder or file at any depth, which covers the git directories of worktrees and submodules under the main `.git`, and any folder git itself would take for a git directory because it holds `HEAD`, `objects` and `refs` (a bare repository, or one made with `--separate-git-dir`). A tool can therefore not plant a hook, change `.git/config` or `.git/info/attributes`, or repoint a worktree. Reading the rest of `.git` stays allowed.
- **Environment.** Programs anvil starts (`shell` commands, check and acceptance commands, hooks, MCP servers, rule checks, anvil's own git calls, and the probes `anvil doctor` runs (`git --version` through `anvil_core::git::standalone`, `sh -c "echo ok"`) and the `icacls` listing `anvil setup` reads) do not inherit anvil's environment. They receive `PATH`, the home, user and temp variables, the locale (`LANG`, `LC_*` without secret-looking names), `TERM`, `NO_COLOR`, the variables Windows needs to start programs (`SystemRoot`, `windir`, `ComSpec`, `PATHEXT`, `SystemDrive`, `HOMEDRIVE`, `HOMEPATH`, `APPDATA`, `LOCALAPPDATA`, `ProgramData`, the `ProgramFiles` and `CommonProgramFiles` folders, `NUMBER_OF_PROCESSORS`, `PROCESSOR_ARCHITECTURE`, `PROCESSOR_IDENTIFIER`, `OS`, `PSModulePath`), `CARGO_HOME` and `RUSTUP_HOME`, and the names listed in `[tools] pass_env` (`crates/anvil-types/src/child_env.rs`). Provider keys (whatever `api_key_env` names), and any variable whose name contains `KEY`, `TOKEN`, `SECRET`, `PASSWORD`, `PASSWD` or `CREDENTIAL`, are passed only when `[tools] pass_env` lists that exact name. A command in the container executor gets none of these inside the container, only `HOME=/tmp` and `PYTHONDONTWRITEBYTECODE=1`. An MCP server definition (the user's or a trusted repository's) may set extra variables for its server, and its `command`, `args` and `env` may use `${VAR}`, but only for a variable from that same list: a reference to any other variable, such as a provider key, stops that server from starting with an error that names the variable (`McpServer::launch` in `crates/anvil-compat/src/mcp/mod.rs`; tests `a_definition_cannot_copy_a_withheld_variable_into_a_server`, `a_launch_expands_only_variables_children_receive`). There is no exception: `crates/anvil-core/tests/children_start_clean.rs` fails the build when non-test code builds a `Command` without `env_clear` within a few lines.
- **anvil's own git calls.** anvil runs git in the project itself to snapshot and diff a session's changes, to commit the items of `anvil build`, and to list changed files for `anvil rules check` and tracked files for `anvil scan-keys`. The model does not choose these commands. They start from the same cleared environment, plus the author and committer identity variables and the variables that locate the user's own git config (`GIT_VARS`); keys, tokens, `GIT_DIR` and `GIT_SSH_COMMAND` do not reach them. The repository's own config (`.git/config`, what it includes, `config.worktree`) is not the user's, so every one of these calls goes through `anvil_core::git::command` (`crates/anvil-core/src/git.rs`), which passes these as `-c` settings, which beat every config file:
  - `core.hooksPath=/dev/null`: no hook runs, including on build commits and checkouts (the user's own hooks in `.git/hooks` do not run on these commits either);
  - `core.fsmonitor=false`: no file system monitor program;
  - `--no-pager`, `core.editor=:` and `sequence.editor=:`: no pager or editor (git treats `:` as no editor);
  - `protocol.allow=never`: no remote is contacted, so `core.sshCommand`, credential helpers and proxies never run.

  Diffs also pass `--no-ext-diff --no-textconv`, so `diff.external` and the diff drivers named in `.gitattributes` never run. Aliases need nothing: git never lets an alias replace a built-in command, and anvil runs built-in commands only. Clean and smudge filters and commit signing programs cannot be switched off from the command line without also switching off the user's own (Git LFS, a signing key). So when the repository's own config names one (`filter.<name>.clean`, `smudge` or `process`, `gpg.program` or `gpg.<format>.program`), anvil refuses to run git there and names the key to remove; the same keys in the user's or the system's config are the user's choice and are used. This needs git 2.26 or later (`git config --show-scope`). A test fails the build if non-test code starts git in any other way.
- **The shell.** `[shell] mode` in the user's configuration, or in the managed policy, which beats it, decides how the `shell` tool runs commands (`crates/anvil-types/src/shell.rs`, `crates/anvil-core/src/tools/shell.rs`, `crates/anvil-cli/src/wiring/shell.rs`):
  - `off`: the tool is not registered; detected and planned checks do not run; `anvil build` refuses to start.
  - `allowlist`: the command is split by a conservative parser into an argument vector and started directly, with no shell interpreter. `;`, `&`, `|`, `<`, `>`, backticks, `$(`, parentheses, braces, line breaks and NUL are refused. The words must match an argument-prefix pattern such as `cargo test *` (`*` only at the end) in every layer: the policy's `[shell] allow`, the user's, and each `shell_programs` list, which counts as one layer of `<program> *` patterns. The program must be named, not given as a path. Because a pattern's `*` leaves the remaining arguments to the model, they are checked too (`shell::argument_refusal` in `crates/anvil-core/src/tools/shell.rs`, applied by the registry and again by `run_command`): no argument, value after `=` or attached short-option value may name a path outside the project (one starting with `~`, or absolute, a drive or UNC path or climbing with `..`, that resolves outside); git may take no option before its subcommand except `--no-pager`, `-P`, `--no-optional-locks`, `--literal-pathspecs`, `--no-replace-objects`, `--version` and `--help`, and never `--output`, `-o`, `--no-index`, `--ext-diff`, `--textconv`, `--open-files-in-pager` or `-O` after it. Allowlisted git starts through `anvil_core::git::allowlisted`: the same `-c` settings as anvil's own git calls, `--no-ext-diff --no-textconv` after diff subcommands and `--no-textconv` after `blame`, and a refusal when the repository's own config sets an alias, `diff.external`, a diff driver's `textconv` or `command`, a merge driver, a diff or merge tool, a credential helper, `core.askPass`, `core.sshCommand`, `core.gitProxy`, `core.alternateRefsCommand`, `core.worktree`, `interactive.diffFilter`, a submodule `update` command, a filter or a signing program, or when the subcommand is an alias from any config file. Tests: `crates/anvil-core/src/tools/allowlist_tests.rs`, `allowlisted_git_refuses_repository_aliases_and_programs` in `git.rs`. What allowlist mode does not cover: an allowed program's own behaviour (build scripts, tests, recipes), and programs the user's own git config names.
  - `ask` (the unmanaged default): the command runs in the configured shell after the permission rules.

  In every mode the built-in deny categories refuse network clients (`curl`, `wget`, `Invoke-WebRequest`, `iwr`, `Invoke-RestMethod`, `irm`, `nc`, `ncat`, `netcat`, `ssh`, `scp`, `sftp`, `ftp`, `Start-BitsTransfer`, `bitsadmin`), `git push`, `git clone`, `git remote add` and `set-url`, package installs (`pip install`, `npm install`, `cargo install`, `gem install`), privilege tools (`sudo`, `runas`, `doas`) and `rm -rf`, `Remove-Item -Recurse`, `git push --force` and `git reset --hard`, also under `--yes`. Only an `allow` rule whose pattern names the command (`shell:curl *`; a bare `shell` or `shell:*` does not), or an allowlist pattern in every layer that names it (`git push origin *`), lifts one. A git alias defined on the command line (`git -c alias.p=push p`, `--config-env=alias...`) is its own category, "git alias definition", because it can rename any subcommand (`deny_category`; test `a_git_alias_defined_on_the_command_line_is_a_deny_category`). In `ask` mode these checks match text, which a shell can get around; they are a guard rail. In `allowlist` mode they hold together with the argument checks above, which refuse every git option before the subcommand. The container is the boundary for what an allowed program does.

  With `executor = "container"` and a `[shell.container]` table, each command runs through `docker` or `podman` as `run --rm --pull=never --network none --read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges --user <user> --pids-limit <n> --memory <m>` with the workspace bind-mounted at `/workspace` as the only host folder, and its `.git` (when present) mounted again read-only on top, so a command in the container cannot plant a hook or change the git config that the user's own git reads later on the host (`container_args`; test `the_workspace_git_folder_is_mounted_read_only_over_the_workspace`). The user is `uid[:gid]`, each a number or a name; neither may be root in any spelling (`0`, `00`, `root`), which `ContainerSettings::validate` refuses (`crates/anvil-types/src/shell.rs`; test `a_container_user_or_group_of_root_is_refused_in_every_spelling`). The default is `65534:65534`, 256 processes and 2 GB. A timed-out container is killed by name. What remains: the rest of the workspace is writable by design, so a container command can change any project file, including scripts and build files that run later on the host (a `build.rs`, a `justfile`, a test); review the diff before running the project outside the container. When `.git` is a file (a worktree or submodule), the folder it points to is outside the workspace and not mounted at all.

## Running in a repository you do not trust

A repository you clone cannot change how anvil treats you:

- Its `.anvil/config.toml` may only add `deny`, `ask` and `shell_programs` under `[permissions]`. A `[providers]` (and so any `base_url`), `[roles]`, `[tools]` (the shell and check programs, `pass_env`, `extra_dirs`), `[network]` or `[shell]` table, or an `allow`, `default` or `allow_tools` permission key, stops anvil with an error that names the key and the file; any other key is ignored with a warning (`crates/anvil-types/src/project.rs`). Its `.anvil/permissions.toml` may add the same three keys and `allow` rules; `default` and `allow_tools` there are errors too.
- Its `.anvil/.env` is never loaded.
- Its hooks, MCP servers, skills, slash commands, agents, instruction files (`ANVIL.md`, `CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md`, nested `CLAUDE.md` files) and `.anvil/permissions.toml` `allow` rules do not take effect until the user trusts the repository (`crates/anvil-cli/src/trust.rs`). The first interactive session lists every item, with the command line of each hook and MCP server and every variable an MCP server definition sets, exactly as written in the file (`${VAR}` references are shown, not expanded), and asks once. The answer is kept in `~/.anvil/trust.toml`, keyed by the repository's full path with symlinks resolved, together with a SHA-256 digest (`fingerprint`) over `.anvil/permissions.toml`, `.anvil/settings*.json`, `.claude/settings*.json`, `.mcp.json`, the root and nested instruction files and the text they import, every file inside the repository that one of its hooks or MCP servers names as its program or an argument, and every file under the project's `skills`, `commands` and `agents` folders in `.claude` and `.anvil`. A repository with a symbolic link or junction in those folders, or in place of them or of `.claude` and `.anvil`, is never trusted (`linked_item`, test `a_repository_that_links_an_agent_is_never_trusted`): the loaders follow links, and a target can change without the repository changing. When any of them changes, is added or is removed, the stored trust no longer counts and the user is asked again; a refusal stays whatever changes. With `--plain`, `--yes`, no terminal, or a command that never prompts (`doctor`, `build`), an undecided or changed repository is untrusted: nothing it ships takes effect, nothing is recorded, and a note on stderr and a warning in the log say so. Trust recorded before digests were kept no longer counts. `anvil trust` shows the list and asks again; `anvil trust --revoke` withdraws trust. Under a managed policy a repository can be trusted only when `[projects] allow_trust = true`; otherwise `anvil trust` refuses to record trust, nothing the repository ships takes effect whatever the user decided, and its `deny` and `ask` rules still apply.
- Even in a trusted repository, an `@path` import in one of its instruction files may only name a file inside the repository, so a `CLAUDE.md` cannot pull `~/.ssh/...` into the prompt (`crates/anvil-compat/src/instructions.rs`).

## Audit log

Every session (`run`, `chat`, `resume`, and each work item of `anvil build`) opens `audit.jsonl` in its session folder before its first model request (`SessionAudit::open` in `crates/anvil-cli/src/audit.rs`, `AuditLog` in `crates/anvil-audit/src/audit/log.rs`). Records are written the moment an event happens, on the thread that emits it, so a tool call comes before the permission decision made for it and its result after.

- **Each record** has `seq` (from 0), `ts` (UTC), `session`, `agent` (`main` or the subagent's name), `user`, `host`, `version`, `commit` (the build's commit or `unknown`), `binary_sha256`, `policy` (`sha256:<hex>` of the policy file or `unmanaged`), the `event` with a `type`, `prev` (the previous record's hash; 64 zeros for the first) and `hash`.
- **Canonical form.** The hash is the SHA-256 of the record's compact JSON with its fields in that order and without `hash`; the stored line is that JSON with `,"hash":"<hex>"` before the closing brace. No field is a floating-point number. `crates/anvil-audit/src/audit/chain.rs` documents it with a ten-line Python check, so a reviewer can verify a file without anvil.
- **Commands.** `anvil audit verify <session id or file>` walks the chain and exits 1 at the first break, naming the line; `anvil audit show <session id or file>` prints one line per record and the verdict.
- **Fail closed.** Under a policy `[audit] required` defaults to `true`: a log or mirror that cannot be opened stops the session before it starts, and a failed write refuses every later model request, tool call and command, stops the loop and exits non-zero. Unmanaged, the log is written but not required: a failed write is logged and the session goes on.
- **What it does not prove** is in "What is not enforced" above: a cut end or a whole rewrite needs the mirror.

## Managed policy

An administrator can install a policy file that nothing below it can loosen (`crates/anvil-types/src/policy/mod.rs`, `crates/anvil-types/src/policy/ownership.rs`, `crates/anvil-cli/src/policy.rs`). `policies/restricted.toml` and `policies/standard.toml` are commented examples, and `docs/ADMIN_GUIDE.md` lists every key with its default.

- **Location.** `/etc/anvil/policy.toml` on Linux and macOS, `C:\ProgramData\anvil\policy.toml` on Windows (`system_path`). The path is a literal in the binary: no environment variable, flag, profile or configuration key moves it or turns it off, and the Windows path is not read from `%ProgramData%`, which a user can change for their own processes. Tests pass another path as a function argument. Test: `the_system_path_is_fixed_per_system`.
- **Ownership.** Before the file is read, `ownership::check` makes sure only an administrator can change it. On Unix the file and its folder must be owned by root and not writable by group or others. On Windows the owner of each must be Administrators, SYSTEM or TrustedInstaller, and no access-control entry may give anyone else a right that writes, deletes or takes over either; the access list is read as SDDL from `Get-Acl` (security identifiers, not localized names), with PowerShell started by its full path, a cleared environment and no profile. A file that fails the check stops anvil with the reason. Tests: `a_policy_file_with_bad_ownership_stops_anvil` (a file the test user created is refused), `unix_needs_root_and_no_group_or_other_write`, `a_user_owned_or_user_writable_descriptor_fails`, `unreadable_descriptors_fail_closed`. Note that a folder created under `C:\ProgramData` inherits a grant that lets Users create files, so the administrator must remove inheritance (`docs/ADMIN_GUIDE.md` has the command).
- **Failure.** A policy file that exists but is not safely owned, cannot be read, does not parse, has an unknown key, names another `version` than 1, or breaks one of its own rules stops anvil before it does anything else, with the reason. Test: `broken_policies_are_errors`.
- **Unmanaged mode.** Without a policy file anvil runs unmanaged. Every session prints `policy: unmanaged` (on stderr with the line renderer, as the `policy` row of the full-screen startup screen), and `anvil doctor` shows it as a skipped `policy` row. With a policy it prints `policy: managed (<path>, sha256:<hash>)`. Tests: `show_and_report_name_each_setting_and_its_layer`, `policy_rows_show_presence_ownership_and_hash`.
- **Precedence.** The policy outranks the user's configuration, a `--profile`, environment variables (a home chosen through `ANVIL_HOME` is checked like any other), command-line flags and the repository. A lower layer that conflicts with it is an error that names the policy key and the setting, never a silent override (`check_flags`, `check_config`, `check_build` in `crates/anvil-cli/src/policy.rs`, `Wiring::with_policy`). Hooks, MCP servers and skills the policy forbids are errors when the user's own files define them, under `~/.anvil` or `~/.claude` alike; a developer with Claude Code hooks or skills in `~/.claude` removes them, or the administrator allows them. One exception is deliberate: the same items shipped by a trusted repository are left out with a note on stderr naming the policy key instead of stopping anvil, so a trusted repository that ships a `.mcp.json` stays usable under a policy that turns MCP off. Tests: every test in `crates/anvil-cli/src/wiring/policy_tests.rs`, including `a_profile_cannot_loosen_the_policy`, `a_home_chosen_through_anvil_home_is_still_under_the_policy`, `the_users_hooks_conflict_and_project_hooks_do_not_load` and `mcp_servers_need_the_mode_and_a_matching_name_and_program`; `skip_flags_are_refused_with_the_policy_key`; `a_user_configuration_that_conflicts_with_the_policy_stops_the_session` in `main.rs`.
- **Keys.** Every key except `version` and `[network] allowed_hosts` defaults to the restrictive choice.
  - `version = 1`: required.
  - `[network] allowed_hosts`: the only `host:port` pairs a provider or HTTP MCP server may name; required. `require_tls` (default `true`): plain http only to loopback. `ca_bundle` (default: the system trust store): a PEM file whose certificate authorities replace the system's. `client_cert` and `client_key` (together, default none): a PEM certificate and key presented for mutual TLS. `proxy` (default `none`): `none`, `system` or an http(s) URL without credentials. The paths must be absolute. Tests: `the_network_table_takes_tls_files_and_a_proxy_mode`, `the_policy_network_table_sets_how_connections_are_made`.
  - `[models] providers`, `models`: the provider names and model names the configuration may use; empty means any.
  - `[permissions] deny`, `ask`: rules added on top of every other layer; a user or profile `allow` rule that the policy's `deny` or `ask` covers is an error. `allow_yes`, `allow_allow_tool` (default `false`): whether `--yes`, and `--allow-tool` or `permissions.allow_tools`, may be used; with `allow_yes` off, a `[permissions] default = "allow"` in the user's configuration, a profile or a saved rules file is an error too, because it approves unnamed calls without a person. `allow_always` (default `false`): whether the `always` answer saves a rule and saved rules under `~/.anvil/permissions/` are read; when off the prompt does not offer it, an `always` answer counts for the session only, and a saved rules file is an error. `require_plan_approval` (default `false`): a person approves the plan of every `anvil run` and chat session, even under `--yes`; in `anvil build` it covers only the top-level build plan.
  - `[files] extra_roots`: folders outside the workspace the file tools may read, never write; `[tools] extra_dirs` in the user's configuration is an error under a policy. `deny`: path globs the file tools refuse and searches skip, on top of the built-in secret list, inside the workspace too.
  - `[features] mcp` (`off`, `allowlist` with `mcp_servers` entries that name the server and either its program, `command`, or its `url`, or `on`; an HTTP server also needs its `host:port` in `allowed_hosts`; test `http_mcp_servers_need_a_url_rule_and_an_allowed_host`), `hooks`, `skills` (`off`, `bundled`, `local`), `memory` (when off nothing under `~/.anvil/memory` is read or written and the end-of-session summarizer does not run), `build` (`anvil build`), `delegation` (the `delegate` tool). All default to off.
  - `[projects] allow_trust` (default `false`): whether a repository can be trusted at all.
  - `[shell] mode` (default `off`: no `shell` tool), `allow` (the patterns of `allowlist` mode), `executor` (default `host`) and `[shell.container]` (`runtime`, `image`, `user`, `memory`, `pids_limit`). The stricter of the policy's and the user's mode applies and the user's allowlist can only narrow the policy's; a looser user mode, another executor, a user `[shell.container]`, or a `[tools] check` the mode would not run is an error naming the key. Tests: `user_shell_settings_that_loosen_the_policy_are_errors_naming_the_key`, `a_shell_table_with_an_allowlist_and_a_container_parses`, `broken_policies_are_errors`.
  - `[data] transcript_dir`, `retention_days`: where session folders go, and how many days they are kept; older ones are deleted when a session starts. `redaction` (default `true`): whether secrets are redacted; only the policy can turn it off. `patterns` (default none): `{ kind, regex }` entries redacted as `[REDACTED:<kind>]` besides the built-in shapes; a pattern that does not compile, matches the empty string or has a kind other than lowercase letters, digits and `_` stops anvil. `transcript` (default `"off"`): `"full"`, `"metadata"` or `"off"`, as in "Files anvil writes". Tests: `the_data_table_sets_redaction_patterns_and_the_transcript_mode`, `a_metadata_transcript_keeps_sizes_and_digests_but_no_text`.
  - `[limits] session_tokens`, `build_tokens`, `build_usd`: ceilings. A larger value set by the user or a flag is an error; without one, the ceiling is used.
  - `[audit] required` (default `true` under a policy): a session runs only while its audit log can be written. `mirror_dir` (default none): an absolute folder every record is also written to. `record` (default `"digest"`): prompts and tool arguments as size and SHA-256, or `"full"` for the redacted text. Tests: `audit_is_required_under_a_policy_not_unmanaged_and_a_mirror_must_be_absolute`, `the_restricted_example_requires_the_audit_log`.
- **Subagents.** Delegated agents use the same registry rules, file boundary, shell mode, allowlist, runner and policy as the session, through the same two functions. Tests: `a_subagent_gets_the_same_policy_rules_and_file_limits`, `subagents_are_confined_like_the_session`.
- **Unattended use.** `--yes` is an error unless `allow_yes = true`, `anvil build` is an error unless `[features] build = true`, and `anvil build` is also an error while the shell is off; none of them is silently downgraded. Tests: `skip_flags_are_refused_with_the_policy_key`, `build_follows_the_feature_switch_and_the_ceilings`, `the_shell_is_off_under_a_policy_unless_the_policy_turns_it_on`.
- **Commands.** `anvil policy show` prints every key of the policy schema with the layer that set it (`policy` or `default`, an unset key as `(default: ...)`), then every user setting the policy constrains with theirs (tests `policy_lines_name_every_key_of_the_schema_set_or_not`, `policy_show_covers_every_user_key_the_policy_constrains`). `anvil policy check <file> [--ownership]` validates a file for an administrator before rollout and exits 1 with the reasons. `anvil doctor` has `policy`, `policy:ownership` and `policy:sha256` rows.
- **Where it is applied.** At startup in `crates/anvil-cli/src/main.rs` (loading, flags, configuration, `anvil build`, trust), and inside a session in one function, `Wiring::with_policy` in `crates/anvil-cli/src/wiring.rs`, plus `Wiring::registry` and `Wiring::tool_context`, which subagents share.

## Release builds

- **Trigger.** `.github/workflows/release.yml` runs only when a version tag (`v*`) is pushed; pushes to `main` publish nothing. A test in `crates/anvil-types/tests/workflows.rs` (`release_runs_only_on_version_tags_and_builds_locked`) fails if the trigger changes or a build drops `--locked`.
- **Builds.** `anvil-cli` is built in release mode with `--locked`, from a clean state without a build cache, on GitHub-hosted runners for `x86_64-unknown-linux-gnu`, `x86_64-unknown-linux-musl`, `x86_64-pc-windows-msvc` and `aarch64-apple-darwin`, with the toolchain pinned in `rust-toolchain.toml`.
- **Assets.** Besides the binaries, each release carries `SHA256SUMS`, `anvil.cdx.json` (a CycloneDX 1.5 SBOM of the anvil binary's dependencies for every platform, made with `cargo-cyclonedx`), and `anvil-<version>-vendored-src.tar.gz` (the tagged source with every dependency vendored, for an offline build; see "Building offline" in `README.md`). The release notes are the version's section of `CHANGELOG.md`.
- **Provenance.** Every asset listed in `SHA256SUMS` gets a GitHub artifact attestation (SLSA build provenance, signed through Sigstore) made by `actions/attest`. `gh attestation verify <file> --repo EliFebres/anvil` checks that a file was built by this repository's release workflow from the tagged commit. This proves where and how a file was built; it is not a code signature from a publisher's certificate, and Windows and macOS will still treat the binaries as unsigned.
- **Workflow permissions.** `release.yml` is the only workflow that may write, and only to `contents` (the release), `id-token` (the attestation's signing certificate) and `attestations`. Its build jobs narrow themselves to `contents: read`. `ci.yml` is read-only. `crates/anvil-types/tests/workflows.rs` refuses any other write grant, and any job-level block that widens instead of narrowing.
- **Pinned actions.** Every action is pinned to a full commit SHA with its version in a comment (`every_action_is_pinned_to_a_commit_sha`). Dependabot (`.github/dependabot.yml`) proposes updates to actions and Cargo dependencies as pull requests; nothing merges without review.
- **Dependency gate.** `cargo deny check` runs in CI (`ci.yml`, job `deny`) against `deny.toml`: every RustSec advisory fails the build unless listed with a reason (one is: `chrono` is unmaintained, with no known vulnerability), only the permissive licenses listed there are accepted, `openssl-sys`, `openssl` and `native-tls` are banned so TLS stays on rustls, and crates.io is the only allowed source. `just deny` runs the same check locally.
- **Ownership.** `.github/CODEOWNERS` requires the owner's review for every path.
- anvil has no self-update. A newer binary comes from whoever distributes anvil to the user.
