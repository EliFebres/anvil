# CLAUDE.md

This is a Cargo workspace (Rust 2024 edition) containing `anvil`. Anvil is a coding agent harness for open-weight models in regulated, restricted-network environments: everything above the model on the machine where it runs (what the agent may read, run, send and store, who controls those limits, and what record is left behind). Read the conventions first; they are not optional.

## Conventions

- Readability first: an intermediate Rust programmer must be able to follow any function without reading another file. YAGNI, DRY, orthogonality: a change in one crate must not require changes in another unless the shared type in `anvil-types` changed.
- Every public item gets a doc comment in Google-docstring shape: one-line summary, blank line, `# Arguments`, `# Returns`, `# Errors`, `# Panics` where they apply. Private items get a one-line summary.
- Validate at boundaries with assertions and descriptive errors: `thiserror` error enums per crate, `anyhow` only in the `anvil` binary (`anvil-cli`). Invariants inside a function use `debug_assert!` with a message.
- Minimal inline comments. A comment explains why, never what.
- Async runtime: tokio. HTTP: reqwest with rustls (no OpenSSL, so Windows builds are painless). Serialization: serde + serde_json + toml. CLI: clap derive. Logging: tracing with a JSON file sink and a human console sink.
- No `unwrap()` outside tests. No `unsafe`.
- Tests live next to the code (`#[cfg(test)]`) plus `tests/` for integration. Use `insta` for snapshot tests of prompts and tool schemas, because those drift silently.
- `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test` must pass before any commit. Add a `justfile` with `just check` that runs all three.
- The agent was once called by another name. That name may not appear anywhere in the tree; `just no-old-name`, part of `just check` and CI, fails on it.
- Every workflow declares a top-level `permissions:` block with the minimum it needs. `release.yml` gets `contents: write`, `id-token: write` and `attestations: write` (for build provenance); everything else gets `contents: read`. `cargo test -p anvil-types` checks every file in `.github/workflows/`.
- `SECURITY.md` is written for someone deciding whether anvil may run on their machines. A change that adds a network destination, a file anvil stores data in, a way a key is read, or a default permission updates it in the same commit.
- A security claim needs a test. A document (README.md, SECURITY.md, anything in `docs/`) may describe a control as present only when code enforces it and a test proves it, and that test is listed in `docs/SECURITY_TESTS.md` against the claim, with the file it lives in. `cargo test -p anvil-types --test docs_match_code` fails when a test named there does not exist or is not in the file named, and when `docs/ADMIN_GUIDE.md` and the policy schema disagree about which keys exist. Renaming or removing a listed test means updating that file in the same commit. Never write that anvil "complies with" or "is certified for" a standard; say which controls it supports and how (`docs/CONTROLS.md`).
- Documents use plain, professional prose: no em dashes, no marketing words.

Workspace lints enforce part of this mechanically: `unsafe_code = "forbid"`, `missing_docs = "warn"`, and `clippy::unwrap_used = "warn"` (allowed in tests via `clippy.toml`). With `-D warnings` these are hard failures.

## Crates

**`anvil-types`** holds shared types only: provider and roles config (`coder`, `summarizer` and the optional `planner`, `worker` and `reviewer`), the skill manifest and the session status file (`status.rs`), plus the validators for each. Its only logic is validation. It also owns loading: the user's anvil config (`config::load`), the tightening rules a repository may add (`project`), the trust decisions (`trust`) and the `.env` file (`dotenv`), plus the one list of environment variables child processes receive (`child_env`), shared so core, compat and memory scrub the same way, the `[shell]` table with the conservative command parser its allowlist mode validates commands with (`shell`), and the managed policy file (`policy`). It also holds the secret shapes and the redactor every tool result passes through (`redact`, which `anvil scan-keys` shares) and `private_fs`, through which anvil creates its own files owner-only. Its `tests/` hold the repository-wide checks that need no other crate: `workflows.rs` (workflow permissions, pinned actions, the release assets) and `docs_match_code.rs` (the tests named in `docs/SECURITY_TESTS.md` exist where it says, and `docs/ADMIN_GUIDE.md` lists every policy key). It must never depend on another workspace crate, on tokio, or on reqwest. Every other crate may depend on it.

**`anvil-core`** is the agent loop, tool registry, provider adapters (OpenAI and Anthropic protocols), and context management. The loop plans on the planner and builds on the coder when the two differ, escalates a stuck Build round to the planner, attributes spend per `Role`, and runs the calls of one turn concurrently when their tool says `parallel_safe`; in Plan it refuses a call whose tool says it may write. `tools/shell.rs` holds `run_command`, the one way the shell tool, checks and build acceptance commands start a program (through the shell, directly in allowlist mode, or in a container), and the built-in deny categories. `guard.rs` is the one choke point between a tool and the conversation: it redacts every tool result and hook output and wraps it in untrusted-data delimiters. `net.rs` is the one place an HTTP client is built or held: every request passes the egress check in `HttpRequest::send` before a connection, redirects are off, and a key is attached only for its own `host:port` (`tests/one_http_client.rs`, `clippy.toml` and `deny.toml` enforce it; `anvil-core` is the only crate that may depend on reqwest). `tools/workspace.rs` and `ToolContext::checked_path` are the file boundary, and `tools/permissions.rs` the permission rules, in which every layer below the user only tightens. `git.rs` is the one way anvil starts git in a project: from a cleared environment, with hooks, the file system monitor, pagers, editors and remotes turned off, and refusing a repository whose own config names a filter or signing program (`tests/one_git_entry.rs` enforces it). It depends on `anvil-types` only. It must never depend on `anvil-compat`, `anvil-memory`, `anvil-audit` or the CLI; those plug into it from the outside through the CLI.

**`anvil-compat`** is Claude Code compatibility: SKILL.md, CLAUDE.md, `.claude/commands`, `.claude/agents`, hooks, and the MCP client. It also ships the two built-in agents (`agents/explore.md`, `agents/implement.md`), which a project or user agent of the same name overrides. HTTP MCP servers send through `anvil-core`'s client, and `mcp/approval.rs` pins each server's tool listing by digest. It depends on `anvil-types` and `anvil-core` (to register tools and hooks). It must never depend on `anvil-memory` or `anvil-audit`.

**`anvil-memory`** is cross-project memory and coding-style rules: rules filtered by the project's languages (`languages.rs`) and project templates (`templates.rs`). It makes no model calls; `anvil-cli` supplies the summarizer. It depends on `anvil-types` only. It must never depend on `anvil-core` or `anvil-compat`.

**`anvil-audit`** records content-free usage on the local machine and sums it up for `anvil stats`, and holds the audit log (`audit/`): the record, its canonical form and hash chain, the appender with its mirror, `verify` and `show`. Nothing it writes is sent anywhere. It consumes values the CLI derives from loop events and never calls into the agent loop, so it depends on `anvil-types` only. It must never depend on `anvil-core`. `anvil-cli/src/audit.rs` translates a session's events, decisions and plan answers into audit records and stops a session whose required log fails.

**`anvil-tui`** is the palette and the small pure rendering helpers the full-screen UI draws with: `theme.rs` (`Theme`, `Shade`), `layout.rs` (text fitting, labels, `centered`), `widgets.rs` (panels, label-value rows, progress bars, status tokens), `wrap.rs` and the ANVIL `LOGO`. It never touches the terminal. It depends on no workspace crate except, if ever needed, `anvil-types`.

**`anvil-cli`** is the `anvil` binary: clap argument parsing and wiring only. It is the one place where the `anvil-*` libraries meet, and the only crate allowed to use `anyhow`. `src/status/` writes each session's `status.json` (a pure tracker fed by loop events and by wrappers around the prompt, the plan gate and the memory decider) and lists sessions for `anvil status`. `src/policy.rs` loads the managed policy from its fixed system path and applies the startup parts; `Wiring::with_policy` applies the rest in one place. `src/build/` is `anvil build`: it plans work items on the planner and runs each as one fresh session through the same function `anvil run` calls, so there is no second loop; an item is done only when its acceptance command and the project check pass.

The full-screen UI lives in `crates/anvil-cli/src/tui/` (ratatui + crossterm). Everything under `tui/` is pure except `runner.rs`, which owns the terminal: `App` consumes `UiMsg`s and draws into a frame, so tests drive it with messages and a `TestBackend`. Modules under `tui/` may import `anvil_core`, `anvil_types` and `anvil_tui` types, tokio channels and the UI crates, and nothing else from this crate: never `Wiring`, `anvil_memory`, `anvil_compat` or the usage records. `frontend.rs` gathers what the UI shows into `SessionInfo` and bridges prompts to it. Every color comes from `anvil_tui::theme`. Scripts and CI use `--plain` (or `--yes`, or no TTY) for the line renderer, which must stay byte-identical; `ANVIL_NO_ANIMATION` skips the startup logo animation.

## Repository layout

- `skills/`: Claude Code-format skills that ship with anvil (`skills/<name>/SKILL.md`).
- `SECURITY.md`: what anvil reads, stores and sends, for a reviewer.
- `docs/`: `SECURITY_TESTS.md` (every security claim and its test), `THREAT_MODEL.md` (assets, boundaries, actors, the OWASP agentic mapping), `CONTROLS.md` (NIST SP 800-53 and 800-171 mapping), `DEPLOYMENT.md` (layouts, data flow, shared responsibility), `ADMIN_GUIDE.md` (release verification, air-gapped install, every policy key, rollout, audit collection, upgrades), `PILOT_SCOPE.md`, `ROADMAP.md` (what is not done), `CODE_TOUR.md` (a reading order through the security code), `USAGE.md` (commands and UI), `DECISIONS.md` (every choice and why). `policies/`: the example managed policies (`restricted.toml`, `standard.toml`), each parsed by a test.
- `profiles/`: profiles that ship with anvil, such as `strict.toml`.
- Trunk is `main` and is protected. Changes reach it through pull requests with the required `ci` check (`.github/workflows/ci.yml`).
- Config: the user's `~/.anvil/config.toml` (plus an optional `--profile`). A repository's `.anvil/config.toml` and `.anvil/permissions.toml` may only add `deny`, `ask` and `shell_programs` rules, and a loosening key in them is an error (`anvil-types/src/project.rs`); its `permissions.toml` `allow` rules, hooks, MCP servers, skills, commands, agents and instruction files take effect only once the user trusts that exact content (`anvil-cli/src/trust.rs`, `~/.anvil/trust.toml` with a SHA-256 digest). File tools never write the files that grant power (`grants_power` in `anvil-core/src/tools/workspace.rs`) or `~/.anvil`. `anvil config init [--global]` writes a template.
